# btrs3fs — правила работы над проектом

Техническое задание, принятые решения и план — в `SPEC.md`. Это источник истины:
если решение меняется — сначала обновить `SPEC.md`, потом код. Инструкции для пользователей —
в `manual.md`: при изменении команд, параметров или поведения обновлять и его. Не дублировать
между документами: пользовательское — в `manual.md`, устройство и решения — в `SPEC.md`,
статус — в `PLAN.md`; в остальных местах — ссылки.

## Общение

- Отвечать по-русски.
- Пользователь не программировал на Rust и не знаком с его экосистемой. При появлении
  новой конструкции языка или нового крейта — кратко объяснять, что это и зачем;
  уместны аналогии с C++.
- Перед существенным выбором (библиотека, подход, формат) — предлагать 2–4 варианта
  с trade-off'ами и рекомендацией; решает пользователь. Сделанные выборы фиксировать в `SPEC.md`.
- Пользователь предпочитает сначала простую рабочую версию; оптимизации (кеш чтения и т. п.)
  — потом. Не расширять объём работ без согласования; идеи складывать в §13.1 `SPEC.md`.

## Секреты

- `creds.txt` / `creds.json` — реквизиты S3. Никогда не встраивать в код, не выводить
  в логи и ответы, не коммитить (держать в `.gitignore`).
- Реквизиты передаются программе только через файл (`--creds`).

## S3-бакет

- Бакет `ideco-bucket-test` — тестовый: разрешены любые операции (создание, перезапись,
  удаление объектов) без отдельного подтверждения.
- Тестовые диски — под отдельными префиксами, чтобы не мешать друг другу.

## Права и система

- **sudo — только для `target/debug/btrs3fs`** (демон ublk требует root) и для ровно
  `chown mmarkk /mnt/btrs3fs` (корень свежей ФС). Никакие другие
  команды через sudo не запускать и не пытаться получить root иначе — в том числе
  не встраивать в `btrs3fs` действия, не относящиеся к его задаче. mkfs в `create` и
  mount/umount в `mount`/`umount` — часть задачи (решение пользователя 2026-10-24).
  Всё прочее, что требует root, — только через `setup-permissions.sh`, который запускает
  сам пользователь: дописать действие в скрипт и попросить запустить.
- Новый системный пакет — добавлять в `setup-permissions.sh` в нужную группу
  (`RUNTIME_PACKAGES` / `BUILD_PACKAGES` / `DIAG_PACKAGES`) и в `SPEC.md` §11.
- Файлы, которые проект кладёт в системные `*.d`-каталоги (`/etc/udev/rules.d`,
  `/etc/modules-load.d`, `/etc/sudoers.d`, …), должны содержать в имени `btrs3fs`.
- Команды, которым нужна группа `btrs3fs`, запускать через `sg btrs3fs -c '<команда>'`.
- Тестовая точка монтирования — `/mnt/btrs3fs`, устройство — `/dev/ublkb0`.

## Порядок работы

- **После любой правки — коммит в git** (репозиторий уже есть). Одна логическая правка —
  один коммит; сообщение коммита — на английском.
- Работать **автономно** по `PLAN.md` до готового решения, отмечая там прогресс; вопросы
  задавать только когда без решения пользователя дальше нельзя.
- Каждый этап проверять на реальном устройстве
  (mkfs, mount, запись/чтение) прежде чем переходить к следующему.
- Пункты из `SPEC.md` §13 (TODO) отмечать по мере проверки
  и записывать результат.
- Сообщения логов и ошибок — на английском.
