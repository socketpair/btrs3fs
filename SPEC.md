# btrs3fs — техническое задание

Зонированное блочное устройство (zoned block device) в пространстве пользователя
на базе **ublk**, данные которого хранятся в **S3** (Yandex Object Storage).
Поверх устройства монтируется **btrfs в zoned-режиме**.

Документ — единственный источник истины по принятым решениям. При изменении
решения — обновлять здесь.

---

## 1. Ключевые решения

| Вопрос | Решение | Почему / что отвергнуто |
|---|---|---|
| Язык и ublk | **Rust + `libublk`** (0.4.x) | В `libublk` есть `UBLK_F_ZONED` и `ZonedAppendRes`; эталон — zoned target в `rublk`. Go отвергнут: нет готовой Go-библиотеки ublk с зонами, пришлось бы писать io_uring/ublk-слой вручную. C (`ublksrv`) — неудобный S3-клиент. |
| Механизм дозаписи в объект | **Yandex PATCH** с `Content-Range` | Стандартный S3 не умеет дописывать. Переносимая эмуляция (`UploadPartCopy` + multipart) — отложена. |
| S3-клиент | **`reqwest` + `aws-sigv4` + `quick-xml`** | `aws-sdk-s3` не умеет произвольный метод PATCH и тяжёлый; `rust-s3`, `object_store` — тоже без частичной записи. Подпись SigV4 не зависит от метода. |
| Размер зоны | **32 МиБ**, capacity = size | Ядро и btrfs требуют степень двойки. 32 МиБ / 4 КиБ = 8192 дозаписи ≤ лимита 10 000. |
| Кеш записи | **только RAM** | Устройство объявляет volatile write cache — потеря неподтверждённых FLUSH данных при падении допустима. |
| Кеш чтения | **нет** (отложено, §13.1) | Ради простоты. |
| Чтение за указателем записи / пустой зоны | **нули** | Как NVMe ZNS (без DULBE), `null_blk`. Ошибка ломала бы probing blkid/udev. |
| Хранение состояния FINISH | **не храним** | См. §4.4. |
| Блокировка от двойного подключения | **нет** (отложено, §13.1) | |
| Права | **демон от root**; в разработке — sudo только на `target/debug/btrs3fs` | Зонированный ublk без root невозможен, см. §11, §13.3. |

## 2. Геометрия устройства

| Параметр | Значение |
|---|---|
| Логический / физический блок | **строго 4096 байт** (не 512): `logical_block_size = physical_block_size = 4096` |
| Размер зоны | 32 МиБ (33 554 432), степень двойки — обязательно |
| Zone capacity | = размер зоны |
| Тестовый диск | 10 ГиБ = **320 зон** |
| Зоны | все sequential-write-required, conventional зон нет |
| max_open_zones / max_active_zones | 1024 / 1024 (из `disk.json`); если ≥ числа зон — ядру сообщается 0 (без лимита) |
| Что видно в sysfs | при «без лимита» ядро само ставит `max_open_zones = min(128, число зон)` — размер пула плагов записи (`block/blk-zoned.c`); это подсказка ядра, движок принимает больше |

Ограничения проверяются в `create`: `zone_size` — степень двойки и кратен 4096;
`disk_size` кратен `zone_size`; `zone_size / 4096 ≤ 10000` (лимит дозаписей в объект).

Btrfs zoned хранит суперблоки в фиксированных зонах по смещениям 0, 512 ГиБ, 4 ТиБ —
диск больше 512 ГиБ получает вторую копию.

## 3. Хранение в S3

### 3.1. Раскладка бакета

```
<prefix>/disk.json            конфиг диска
<prefix>/0000000000000000     зона 0
<prefix>/0000000002000000     зона 1 (смещение 32 МиБ)
...
```

- Имя объекта зоны — байтовое смещение начала зоны, **16 hex-цифр, нижний регистр, лидирующие нули**.
- Объект существует только если в зону что-то записано и сброшено. Нет объекта ⇒ зона пустая.
- **Размер объекта = персистентный указатель записи зоны.** Отдельные метаданные не нужны.
- Бакет должен быть с **выключенным версионированием** (требование PATCH).

### 3.2. `disk.json`

```json
{
  "version": 1,
  "disk_size": 10737418240,
  "zone_size": 33554432,
  "max_open_zones": 1024,
  "max_active_zones": 1024,
  "dirty_limit_bytes": 268435456,
  "retry_timeout_seconds": 60,
  "retry_initial_delay_ms": 100,
  "retry_backoff_factor": 2.0,
  "nr_queues": 4,
  "queue_depth": 128
}
```

| Поле | Смысл |
|---|---|
| `disk_size` | Размер устройства в байтах |
| `zone_size` | Размер зоны в байтах |
| `max_open_zones`, `max_active_zones` | Лимиты зон, сообщаемые ядру |
| `dirty_limit_bytes` | Мягкий лимит несброшенных данных в RAM на устройство (§5.3) |
| `retry_timeout_seconds` | Общий бюджет повторов одной операции S3 |
| `retry_initial_delay_ms` | Первая пауза между повторами |
| `retry_backoff_factor` | Множитель паузы на каждой попытке |
| `nr_queues` | Число очередей ublk (потоков); переопределяется `run --queues` |
| `queue_depth` | Глубина каждой очереди ublk |

`disk.json` пишется командой `create` и при `run` только читается.

### 3.3. Файл с реквизитами доступа

JSON, путь передаётся флагом `--creds`. В коде и логах реквизиты не появляются.

```json
{
  "endpoint": "https://storage.yandexcloud.net",
  "region": "ru-central1",
  "bucket": "ideco-bucket-test",
  "access_key": "...",
  "secret_key": "..."
}
```

## 4. Семантика блочного устройства

Устройство объявляет **volatile write cache + FUA** — иначе ядро не присылает FLUSH/FUA.

### 4.1. Операции ввода-вывода

| Операция | Поведение |
|---|---|
| `WRITE` | Только по `offset == wp` зоны, иначе `EIO`. Данные — в RAM-буфер зоны, ответ сразу. |
| `ZONE_APPEND` | Под замком зоны: `lba = wp`, данные в буфер, `wp += len`. Возвращает `lba` ядру. |
| `WRITE` с FUA | Как WRITE, затем сброс этой зоны в S3 до ответа. |
| `FLUSH` | Сброс всех зон с несброшенными данными (параллельно); ответ — после подтверждения S3. |
| `READ` | `[0, flushed)` — из S3 (`GET` с `Range`), `[flushed, wp)` — из RAM, `[wp, …)` — нули. |
| `DISCARD`, `WRITE_ZEROES` | Не поддерживаются (не объявляются). |

Ошибки (`EIO`): запись не по указателю, в FULL-зону, за пределы zone capacity,
через границу зоны; исчерпан бюджет повторов S3.

### 4.2. Управление зонами

| Операция | Поведение |
|---|---|
| `REPORT_ZONES` | Из состояния в памяти. |
| `ZONE_OPEN` / `ZONE_CLOSE` | Только смена состояния в памяти + учёт лимитов open/active. |
| `ZONE_FINISH` | Состояние → FULL в памяти (не персистится, §4.4). |
| `ZONE_RESET` | Дождаться текущей выгрузки зоны, `DELETE` объекта, обнулить состояние. |
| `ZONE_RESET_ALL` | `RESET` всех непустых зон. |

Машина состояний зон и учёт implicit/explicit open — по модели ZBC/ZNS
(эталон: `null_blk` zoned, `rublk` zoned).

### 4.3. Восстановление при старте

`GET disk.json` → `ListObjectsV2` по префиксу (с пагинацией) → для каждой зоны:

| Размер объекта | Состояние |
|---|---|
| нет объекта / 0 | EMPTY, `wp = 0` |
| `= zone_size` | FULL |
| иначе | CLOSED, `wp = size` |

### 4.4. Почему FINISH не персистится

После перезапуска зона, закрытая через FINISH не до конца, станет CLOSED с указателем
посередине. Для btrfs это безопасно: позиция аллокации в block group берётся из
указателя записи и сверяется с деревом экстентов — btrfs просто увидит свободное место.
При лимите активных зон ≥ числа зон у btrfs почти нет поводов вызывать FINISH.
Если понадобится — пустой маркер `<prefix>/finished/<offset>`, читается тем же List.

## 5. Кеш записи и выгрузка в S3

### 5.1. Выгрузка зоны

- Первая выгрузка зоны (объекта нет) — `PUT`; последующие — `PATCH` с
  `Content-Range: bytes {flushed}-{flushed+len-1}/*`.
- PATCH с явным смещением **идемпотентен**: повтор после потерянного ответа
  перезаписывает тот же диапазон теми же байтами. `PUT` — тоже.
- Одна выгрузка на зону одновременно; параллельные FLUSH **схлопываются**
  (второй ждёт первого и обнаруживает, что выгружать почти нечего).

### 5.2. Число дозаписей

Каждая выгрузка ≥ 4 КиБ, зона 32 МиБ ⇒ не больше 8192 дозаписей в объект даже при
FLUSH после каждой записи. Объединение записей до FLUSH уменьшает число дозаписей.

### 5.3. Лимит грязных данных

- Глобальный счётчик несброшенных байт.
- Превышен `dirty_limit_bytes` ⇒ фоновая выгрузка, начиная с зон с наибольшим
  буфером, не дожидаясь FLUSH (не нарушает семантику: «писать только по FLUSH» —
  оптимизация, а не требование корректности).
- Защита от OOM при недоступном S3: при достижении **2 × `dirty_limit_bytes`** новые
  записи ждут освобождения места.

## 6. Многопоточность и синхронизация

### 6.1. Состояние зоны и инвариант

```
 0 ─────────── flushed ─────────── wp ──────────── zone_size
 │  в S3, неизменно  │  в RAM (chunks) │  не записано (нули)
 │  до RESET         │  ещё не в S3    │
```

```rust
struct ZoneState {           // std::sync::Mutex, по одному на зону
    wp: u64,                 // логический указатель записи (включая RAM)
    flushed: u64,            // подтверждено S3 (= размер объекта)
    chunks: VecDeque<Bytes>, // данные [flushed, wp)
    cond: ZoneCond,
}
struct Zone {
    state: Mutex<ZoneState>,
    upload: tokio::sync::Mutex<()>, // не больше одной выгрузки на зону
}
```

**Инвариант:** RAM покрывает `[flushed, wp)`, S3 покрывает `[0, flushed)`. Байты удаляются
из RAM **только после** подтверждения S3.

### 6.2. Правила

1. **Никакого сетевого ввода-вывода под `state`-мьютексом.** Замок держится микросекунды:
   снять снимок (клоны `Bytes` — только счётчик ссылок), отпустить, идти в сеть.
2. **Порядок захвата фиксирован:** сначала `upload`, потом `state`. Обратного порядка нет.
3. Запись подтверждается ядру только после попадания в `chunks` под замком; FLUSH читает
   состояние под тем же замком ⇒ FLUSH видит все подтверждённые до него записи, даже
   если пришёл в другую очередь.
4. Ошибка выгрузки: `flushed` не двигается, данные остаются в RAM, следующий FLUSH
   повторяет тот же диапазон.
5. Обычные WRITE в одну зону ядро (zone write plugging, ядро ≥ 6.10) отдаёт по одной;
   проверка `offset == wp` — страховка. ZONE_APPEND могут идти параллельно — их
   упорядочивает замок зоны.

## 7. Копирование данных (zero-copy)

- Зоны в ublk требуют **`UBLK_F_USER_COPY`**: данные копируются `pread`/`pwrite` на `/dev/ublkcN`.
- Итого **одно копирование** на запись (ядро → наш `Bytes`) и одно на чтение.
- Zero-copy (`UBLK_F_SUPPORT_ZERO_COPY` / `AUTO_BUF_REG`) **невозможен и не нужен**:
  1. запись подтверждается до FLUSH, а страницы запроса после подтверждения возвращаются
     ядру — данные обязаны быть в нашей памяти;
  2. HTTPS — TLS всё равно шифрует в пользовательском пространстве;
  3. zero-copy запрещён в непривилегированном режиме ublk.
- Буфер зоны — список `Bytes`, а не растущий `Vec` (без переаллокаций с копированием до 32 МиБ).
  Тело PATCH собирается из chunks потоком, без склейки.

## 8. S3-клиент

Свой тонкий клиент: `reqwest` (HTTP, пул соединений, rustls) + `aws-sigv4` (подпись) +
`quick-xml`/`serde` (разбор ответа List).

| Событие | Запрос |
|---|---|
| Первый сброс зоны | `PUT <prefix>/<offset>` |
| Последующие сбросы | `PATCH` + `Content-Range` |
| Чтение сброшенных данных | `GET` + `Range: bytes=a-b` |
| `ZONE_RESET` | `DELETE` |
| Старт | `GET disk.json`, `ListObjectsV2` (пагинация по continuation token) |
| `create` / `destroy` | `PUT disk.json` / `List` + `DELETE` всех объектов |

### Транспорт

| Требование | Как обеспечивается |
|---|---|
| HTTPS keep-alive | Пул соединений `reqwest` (переиспользование по умолчанию); `pool_idle_timeout` 90 с; `pool_max_idle_per_host` ≥ числа параллельных выгрузок. |
| `TCP_NODELAY` (без алгоритма Нейгла) | `ClientBuilder::tcp_nodelay(true)` — задаётся явно, не полагаемся на умолчание. |
| Обнаружение мёртвых соединений | `ClientBuilder::tcp_keepalive(30 с)` (`SO_KEEPALIVE`). |
| Неблокирующие сокеты (`O_NONBLOCK`/`O_NDELAY`) | Всегда: tokio работает только с неблокирующими сокетами. |
| HTTP/2 | Яндекс поддерживает (ALPN `h2`, TLS 1.3; PATCH и Range-GET по h2 проверены 2026-10-23). HTTP/3 не объявляет. |

Версия HTTP — флаг `run --http auto|http1|http2`, по умолчанию `auto` (ALPN → h2).
Компромисс: h2 мультиплексирует все запросы в одном TCP-соединении (нет повторных
рукопожатий, но параллельные крупные выгрузки делят одно окно перегрузки TCP и окна
управления потоком h2 — их нужно увеличить, `http2_adaptive_window(true)`); HTTP/1.1 с пулом
даёт N независимых TCP-соединений. Выбор по умолчанию — по замерам в облаке.

### Повторы

- Повторяемые ошибки: сетевые, таймауты, HTTP 5xx, 429.
- Неповторяемые (сразу ошибка): прочие 4xx (403 неверные ключи, 404 и т. п.).
- Пауза: `retry_initial_delay_ms × retry_backoff_factor^n`, ограничена остатком бюджета.
- Бюджет `retry_timeout_seconds` исчерпан ⇒ операция ядру возвращает `EIO`
  (btrfs уйдёт в read-only), данные остаются в RAM.

## 9. Архитектура процесса

```
 ядро ──ublk──► nr_queues потоков (libublk, свой io_uring + локальный executor)
                   │ WRITE/APPEND → RAM-буфер зоны, ответ сразу
                   │ READ из RAM / нули → ответ сразу
                   │ READ из S3, FLUSH, FUA ──задача──► пул tokio (reqwest → S3)
                   │                                        │
                   ◄──── eventfd «готово» ──────────────────┘
```

- Два цикла событий: io_uring (libublk) и epoll (tokio). Поток очереди спит в io_uring,
  поэтому ответ из tokio будит его через **eventfd**, зарегистрированный в io_uring.
- Общее состояние зон — `Arc<Vec<Zone>>`, доступно всем очередям и tokio.
- Логи — только на английском (`tracing`).

## 10. CLI

| Команда | Что делает |
|---|---|
| `btrs3fs create --creds F --prefix P --size S [--zone-size Z] [...]` | Проверяет параметры, пишет `P/disk.json`. Отказ, если `disk.json` уже есть. |
| `btrs3fs run --creds F --prefix P [--queues N] [--dev-id 0]` | Читает конфиг, восстанавливает зоны, поднимает `/dev/ublkb<id>`. Работает на переднем плане. |
| `btrs3fs detach [--dev-id 0]` | Отказ, если устройство смонтировано (`O_EXCL` на `/dev/ublkbN` даёт `EBUSY`). Иначе SIGTERM демону (pid из `GET_DEV_INFO`) и ожидание выхода. |
| `btrs3fs destroy --creds F --prefix P --yes` | Удаляет все объекты зон и `disk.json`. |

### Остановка (`detach` / SIGTERM / SIGINT)

1. Сбросить все буферы в S3 (с обычной политикой повторов).
2. Удалить ublk-устройство, выйти с кодом 0.
3. Если бюджет повторов исчерпан — **не висеть**: залогировать, какие зоны и сколько байт
   потеряно, удалить устройство и выйти с ненулевым кодом.

## 11. Права доступа и окружение

- **Демону нужен root** (`CAP_SYS_ADMIN`): зонированный ublk требует `UBLK_F_USER_COPY`,
  а ядро запрещает его непривилегированным устройствам (§13.3). Непривилегированный режим
  ublk не используется.
- **Разработка:** единственное правило sudoers — `NOPASSWD` на
  `<repo>/target/debug/btrs3fs` (любые аргументы). Этот файл пересобирается, поэтому тот,
  кто может его переписать, фактически имеет root — решение пользователя (2026-10-23),
  отвергнуты: ВМ `virtme-ng`, root-бинарник в `/usr/local/bin` с ручной установкой,
  привилегированный помощник.
- Второе правило sudoers — ровно `chown <user> /mnt/btrs3fs` (без других аргументов):
  `mkfs.btrfs --rootdir` несовместим с zoned-режимом, а корень новой ФС принадлежит root.
- `sudo` сбрасывает окружение, поэтому уровень логов задаётся флагом CLI, а не `RUST_LOG`.
- `mkfs.btrfs`, `blkzone`, тестовый ввод-вывод — **от обычного пользователя**: группа
  `btrs3fs` с доступом на чтение и запись к `/dev/ublkbN`. Без перелогина:
  `sg btrs3fs -c '<команда>'`.
- Монтирование — без sudo, через строку в `/etc/fstab` с опцией `user`
  (подразумевает `nosuid,nodev,noexec`).
- **Рабочая система:** демон от root через systemd unit.
- Одноразовая настройка — `setup-permissions.sh` (запускает пользователь через sudo).
  Действия:

  | Действие | Что делает |
  |---|---|
  | `install` | Пакеты для работы готовой системы + права: `/etc/sudoers.d/btrs3fs`, группа, udev-правило для `ublkb*`, загрузка модуля, fstab |
  | `uninstall` | Откат прав, удаление группы (пакеты остаются) |
  | `build-deps` | Пакеты для сборки: `rust`, `cargo`, `gcc`, `clang-devel` (libclang для bindgen в `libublk-rs-sys`), `kernel-headers`, `glibc-devel`, `git` |
  | `diag-tools` | Тесты и диагностика: `fio`, `blktrace`, `sysstat`, `strace`, `gdb`, `perf`, `jq`, `awscli2` |

  Пакеты для работы: `kernel-modules-core` (`ublk_drv`), `systemd-udev`, `shadow-utils`,
  `sudo`, `util-linux`, `btrfs-progs`, `ca-certificates`.

Окружение разработки: Fedora 44, ядро 7.2 (`CONFIG_BLK_DEV_ZONED=y`,
`CONFIG_BLK_DEV_UBLK=m`, `CONFIG_BLK_DEV_ZONED_LOOP=m`), Rust 1.99, btrfs-progs 7.1.
