# btrs3fs — техническое задание

Зонированное блочное устройство в пространстве пользователя на базе **ublk**, данные — в
**S3** (Yandex Object Storage), одна зона — один объект. Поверх — **btrfs в zoned-режиме**.

Источник истины по решениям: при изменении решения — сначала здесь. Пользовательское —
`manual.md`, статус работ — `PLAN.md`. Замеры, на которые ссылаются решения, — §12.

## 1. Ключевые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Язык и ublk | Rust + `libublk` из git (`main`, 0.5 до релиза; §9.4) | В `libublk` есть `UBLK_F_ZONED`; эталон — zoned target `rublk`. Go — нет библиотеки ublk с зонами; C (`ublksrv`) — неудобный S3-клиент. |
| Дозапись в объект | `PATCH` (Yandex), `PUT_APPEND` (Ceph RGW Append Object) или `SEGMENTS` (новый объект на каждую выгрузку + фоновая склейка на сервере) — §5 | Стандартный S3 дописывать не умеет. Способ выбирает `create` пробами и пишет в `disk.json`; без дозаписи и без серверной склейки мелких частей (AWS, Яндекс) бакет не годится. Режим `MULTIPART` (склейка на каждую выгрузку) удалён: `SEGMENTS` быстрее в разы (§12). |
| S3-клиент | `reqwest` (только HTTP/1.1) + `aws-sigv4` + `quick-xml` | `aws-sdk-s3`, `rust-s3`, `object_store` не умеют PATCH. HTTP/2 гонит всё через одно TCP-соединение: параллельные GET в 3,5 раза медленнее (§12). |
| Размер зоны | **16 МиБ**, capacity = size, без уплотнения | Степень двойки (ядро, btrfs). PATCH к объекту, выросшему из дозаписей, за ~20 МБ занимает 9–30 с (§12); уплотнение копированием помогает ненадолго — отвергнуто. |
| Кеш записи | Только RAM; устройство объявляет volatile write cache + FUA | Несброшенное по FLUSH при аварии теряется, как у диска с кешем. |
| Кеш чтения | Окно чтения с запасом + LRU (§6) | Повторы обслуживает page cache; окно склеивает холодные чтения соседних мелких файлов. |
| Настройки чтения и выгрузки | Вычисляются из характеристик связи с S3, которые админ меряет командой `measure` и передаёт флагами (§6.1); прямых ручек нет | Лучшие значения в облаке и через интернет различаются в разы (§12); их задают задержка и скорость S3. |
| Чтение за указателем записи | Нули | Как NVMe ZNS и `null_blk`; ошибка ломала бы пробы blkid/udev. |
| FINISH | Пустой объект-метка `<зона>.finished` рядом с объектом зоны (§3.3) | Состояние зон после перезапуска совпадает с тем, что видела btrfs. Метка, а не тег: теги есть не у всякого S3 (Selectel их молча игнорирует), а листинг показывает метку без лишних запросов. |
| Профили btrfs | `single` для данных, метаданных и system (решение пользователя) | Копии DUP легли бы в тот же S3 и не добавили бы сохранности, но удвоили бы запись метаданных и заняли бы лишние активные зоны. |
| Лимиты open/active зон | Не сообщаем | У устройства нет ресурса на зону; малый лимит вешает btrfs (§11). |
| Смерть демона | `UBLK_F_USER_RECOVERY | UBLK_F_USER_RECOVERY_FAIL_IO`, восстановление не используется (§9.4) | Без флагов ядро может зависнуть навсегда; перезапуск без журнала опасен. |
| Блокировка от двойного подключения | Нет (отложено, §13) | |
| Права | Демон от root; в разработке sudo только на `target/debug/btrs3fs` (§10) | Зонированный ublk требует `USER_COPY`, а он запрещён непривилегированным устройствам. |

## 2. Параметры устройства

| Параметр | Значение |
|---|---|
| Блок логический / физический | **4096 / 4096** |
| Зоны | 16 МиБ, capacity = size, все sequential-write-required; тестовый диск 10 ГиБ = 640 зон |
| `max_open_zones` / `max_active_zones` | 0 (без лимита). Ядро само показывает в sysfs `max_open_zones = min(128, зон)` — размер пула плагов записи, подсказка; btrfs берёт её как свой предел активных зон (§11). Поля в старых `disk.json` принимаются и игнорируются. |
| Наибольший запрос | Аппаратный (`max_sectors`) и программный (`queue/max_sectors_kb`) = зона (ublk при user copy — до 32 МиБ, `MAX_ZONE_SIZE`); программный демон ставит сразу после создания устройства, до монтирования. btrfs при монтировании берёт программный и как предел дозаписи данных: меньший дробил бы файлы на экстенты этого размера, перемешанные с соседними файлами (решение пользователя). Параллельность крупного чтения даёт сам демон, деля запрос на части (§6.2). |
| `io_opt` | = зона. Ядро режет запись данных btrfs по `io_opt`: при 4 КиБ дозаписи шли по 4 КиБ и файлы рвались на экстенты по 4 КиБ. Упреждение блочного устройства = 2 × `io_opt`; у btrfs своё — 4 МиБ. |
| Вращающийся | Нет. Для вращающихся зонированных устройств ядро пускает запись во все зоны одним потоком по одной (`zoned_qd1_writes`). На размещение данных btrfs в zoned-режиме признак не влияет; `nossd` лишь склеивает одновременные fsync в одну фиксацию журнала (`tree-log.c`), не измерено. |
| wbt (регулятор фоновой записи) | **Выключен**: демон пишет `0` в `queue/wbt_lat_usec`. Он урезает `WRITE`, когда чтения медленнее 2 мс, — у нас чтения медленные из-за S3, а запись идёт в RAM. `ZONE_APPEND` он не трогает. Ручное выключение переживает смену планировщика udev. |
| Кеш записи, FUA | write back, FUA — иначе ядро не шлёт FLUSH/FUA |
| Планировщик | `mq-deadline` (udev-правило btrfs для host-managed) |
| Идентификация | `lsblk`: `MODEL` = `btrs3fs`, `SERIAL` = `<бакет>/<префикс>`, `REV` = версия сборки; ссылка `/dev/disk/by-id/btrs3fs-<бакет>-<префикс>` (в имени всё, кроме `A-Z a-z 0-9 . _ -`, — `-`). ublk таких полей не передаёт (§11), поэтому демон сразу после старта устройства шлёт синтетическое событие `change <uuid> BTRS3FS=<hex>` в `/sys/block/ublkbN/uevent`: ядро пропускает в значениях только буквы и цифры, а в hex лежат готовые строки `KEY=VALUE`. Правило udev из `setup-permissions.sh` раскодирует их `basenc --base16 -d` (coreutils; сам udev hex не умеет) и сохраняет при следующих событиях (`IMPORT{db}`). Строки длиннее 768 байт (до hex) не передаются — предупреждение в журнал. Файлов не создаёт (решение пользователя). Без правила событие ни на что не влияет. |
| Версия сборки | `<версия пакета>-g<коммит>[-dirty]` из `git describe` (`build.rs`); без git — версия пакета. Её печатает `--version`. |

Проверки `disk.json`: `zone_size` — степень двойки, не больше 32 МиБ и `zone_size / 4096 ≤
10 000` (лимит дозаписей в объект); btrfs сама требует зону ≥ 4 МиБ; `disk_size` кратен зоне. Суперблоки btrfs zoned — в
зонах по смещениям 0, 512 ГиБ, 4 ТиБ.

## 3. Хранение в S3

### 3.1. Раскладка

```
<prefix>/disk.json            параметры диска
<prefix>/0000000000000000     зона 0
<prefix>/0000000001000000     зона 1 (смещение 16 МиБ)
<prefix>/0000000001000000.finished   метка: зона 1 закрыта FINISH (0 байт)
<prefix>/0000000002000000-00000000   SEGMENTS: зона 2, объект с начала зоны
<prefix>/0000000002000000-00340000   SEGMENTS: фрагмент с 0x340000 в зоне
<prefix>/0000000002000000.meta       SEGMENTS: метка: в зоне метаданные btrfs (0 байт)
```

- Имя объекта зоны — смещение зоны, 16 hex-цифр, нижний регистр. В режиме `SEGMENTS` — ещё
  `-` и смещение начала объекта внутри зоны, 8 hex-цифр (решение пользователя): листинг по
  префиксу `<prefix>/<зона>` даёт все объекты зоны и её метки.
- Удаление «по префиксу» (RESET зоны, RESET_ALL, `destroy`, прерывание склеек при старте) трогает
  только ключи, которые разбираются как объекты зон этого диска: другой диск под его префиксом
  (`<prefix>/x/…`) или с префиксом, начинающимся с имени зоны, не задевается. `create` не
  создаёт диск внутри префикса другого диска (у предка есть `disk.json`), а `destroy` требует
  `disk.json` по префиксу.
- Объект есть, только если в зону что-то сброшено. **Указатель записи = размер объекта**, в
  `SEGMENTS` — конец непрерывного покрытия зоны её объектами (§5).
- Версионирование бакета выключено (иначе каждая дозапись копит старые версии объекта).

### 3.2. `disk.json` и реквизиты

- `disk.json` — геометрия, `dirty_limit_bytes`, повторы, очереди; пишет `create`, остальные
  команды только читают; неизвестные поля — ошибка. Поля и умолчания — `manual.md` §6.
- Реквизиты — JSON-файл (`endpoint`, `region`, `bucket`, `access_key`, `secret_key`), только
  через `--creds`; в логах и `Debug` не появляются. Формат — `manual.md` §3.
- Настройки связи с S3 (`--s3-*`) и `--read-cache` — флаги запуска, не `disk.json`: это
  настройка машины.

### 3.3. Метка FINISH

Решение пользователя: пустой объект `<объект зоны>.finished` — рядом со своей зоной (в
листинге сразу за ней) и без конфликта «файл и каталог с одним именем», который дал бы
`<зона>/finished`. Для любого S3, Яндекс тоже.

- FINISH: выгрузить буфер, `PUT` пустой метки. Только после этого зона FULL. Флаг метки в памяти
  ставится до `PUT`: «метка, возможно, есть» — `PUT`, ответ которого потерян, а объект создан,
  RESET всё равно удалит.
- FINISH зоны без данных в S3 ничего не пишет: FULL только в памяти, после перезапуска зона
  EMPTY. Для btrfs это безопасно — данных нет, указатель она берёт из REPORT_ZONES. Так метка
  без данных всегда означает остаток прерванного RESET (§5).
- RESET удаляет метку после объекта зоны (§5).
- Старт: метки приходят в том же `ListObjectsV2`, отдельных запросов нет.
- Теги объектов не используются. Диски, где FINISH был записан тегом, после перезапуска видят
  такие зоны CLOSED — безопасно, лимитов зон устройство не сообщает (§11).

## 4. Семантика устройства

| Операция | Поведение |
|---|---|
| `WRITE` | Только по указателю записи зоны; данные — в RAM-буфер зоны, ответ сразу. |
| `ZONE_APPEND` | Под замком зоны: адрес = указатель, данные в буфер; адрес — ядру. |
| `WRITE` + FUA | Как WRITE, затем выгрузка этой зоны до ответа. |
| `FLUSH` | Выгрузка всех зон с буфером (параллельно, §6.1), ответ после подтверждения S3. |
| `READ` | `[0, flushed)` — S3 (§6), `[flushed, data_end)` — RAM, дальше — нули. |
| `REPORT_ZONES` | Из памяти. |
| `ZONE_OPEN` / `CLOSE` | Только состояние в памяти. |
| `ZONE_FINISH` | §3.3. |
| `ZONE_RESET` | Под замком выгрузки зоны удалить её объекты — начало зоны первым (§5), обнулить состояние. |
| `ZONE_RESET_ALL` | Под замками всех зон всё, кроме `disk.json`, `DeleteObjects` пакетами: сначала начала зон, потом остальное; обнулить состояние. |
| `DISCARD`, `WRITE_ZEROES` | Не объявляются. |

`EIO`: запись не по указателю, в FULL-зону, через границу зоны; исчерпан бюджет повторов S3;
любой ввод-вывод в зону, чей RESET не удался (§5).
Машина состояний зон — по ZBC/ZNS (эталон `null_blk`, `rublk`).

**Старт:** `GET disk.json` → `ListObjectsV2` с пагинацией. Нет данных в начале зоны — EMPTY, а
метки и прочие объекты зоны — остатки прерванного RESET, удаляются до запуска устройства (§5).
Иначе: с меткой FINISH — FULL, размер зоны — FULL, иначе CLOSED с указателем = размеру.

## 5. Запись и выгрузка

- Первая выгрузка зоны — `PUT` (в режиме `PUT_APPEND` — дозапись с позиции 0), следующие —
  дозапись в объект, способ — поле `append` в `disk.json`:
  - **`PATCH`** (Yandex): `PATCH` с `Content-Range: bytes a-b/*`, один запрос;
  - **`PUT_APPEND`** (Ceph RGW): `PUT ?append&position=<flushed>`, один запрос. Ответ обязан
    содержать `x-rgw-next-append-position` = позиция + длина, иначе ошибка (не тихая
    перезапись). RGW дописывает только в объект, созданный дозаписью, отсюда и первая выгрузка
    дозаписью. Повтор после потерянного ответа получает `409` (позиция уже не равна длине):
    тогда `HEAD` — если объект ровно позиция + длина, прошлая попытка удалась;
  - **`SEGMENTS`** (S3 без дозаписи, например Selectel; решение пользователя): каждая выгрузка —
    новый объект `<зона>-<смещение>`, один `PUT`; подробности — ниже.
  - Способ выбирает `create` на пробных объектах под префиксом диска: `PATCH`; на 405/501 —
    две дозаписи `?append` (4 КиБ с позиции 0, затем с 4096), обе с `200` и
    `x-rgw-next-append-position` 4096 и 8192 — `PUT_APPEND`; иначе склейка двух объектов по
    4 КиБ на сервере — `SEGMENTS`; иначе отказ. У дисков без поля — `PATCH`; строчное `patch`
    тоже читается; диски `MULTIPART` больше не поддерживаются (пересоздать).
- PATCH с явным смещением, дозапись RGW с проверкой длины и PUT фрагмента под смещением
  **идемпотентны**: повтор после потерянного ответа даёт тот же объект.
- Одна выгрузка на зону одновременно; параллельные FLUSH схлопываются.

**Режим `SEGMENTS`**
- **Объекты зоны:** у каждого — начало (в имени) и диапазон зоны, который он обслуживает.
  Чтение режется по границам объектов (и по частям GET), окно чтения с запасом может собираться
  из нескольких объектов.
- **Склейка (уплотнение)** — фоновая задача: объекты зоны склеиваются на сервере
  (`CreateMultipartUpload` + `UploadPartCopy` с диапазоном на каждый объект +
  `CompleteMultipartUpload`) в первый объект `<зона>-00000000`, затем склеенные фрагменты
  удаляются (`DeleteObjects`). До 4 зон одновременно, одна зона — никогда дважды одновременно.
- **Когда склеивать** (решение пользователя). Склейка копирует на сервере всю зону, а пользу
  даёт последовательному чтению, поэтому для метаданных она откладывается сильно дольше.
  - Тип зоны: **метаданные**, если в неё хоть раз пришёл запрос с `UBLK_IO_F_META` или обычный
    `WRITE` (btrfs пишет метаданные WRITE, данные — ZONE_APPEND; чтение с META тоже метит
    непустую зону); иначе данные. Как только зона стала метаданными, склейщик сразу (под замком
    выгрузки зоны, чтобы RESET не оставил метку у пустой зоны) ставит пустой объект
    `<зона>.meta` (решение пользователя); при старте он из того же листинга восстанавливает тип,
    метка без данных зоны — след прерванного RESET, удаляется. RESET удаляет её вместе с зоной
    (всё под префиксом зоны). Тип неизвестен — правила данных.
  - По каждой зоне: время последней записи (`CLOCK_BOOTTIME`, учитывает сон; при старте — время
    старта) и скользящее среднее интервала между записями (EWMA, вес новой 1/5).
  - **Простой:** зона не менялась дольше T = k × средний интервал, ограниченного: данные k = 4,
    30 с … 10 мин; метаданные k = 8, 5 мин … 1 ч; без интервала — нижняя граница.
  - **Много фрагментов:** больше N = 4 × размер зоны / часть GET (§6.1; не меньше 8, не больше
    1024), для метаданных — 4 × N; и только если после прошлой склейки добавилось не меньше 1/8
    уже склеенного (иначе зону каждый раз копировали бы ради крошки).
  - **FULL:** данные — сразу, вне очереди; метаданные — только по простою (такие зоны часто
    скоро сбрасываются balance/reclaim).
  - Кнопка на странице — все раздробленные сразу. Простой проверяется раз в 5 с. Зона, целиком набранная в RAM, уходит одним `PUT` и склейки не
  требует.
- **Гонка с RESET** (решение пользователя: проверка поколения). Опасно только завершение
  склейки: после RESET и новой записи первый фрагмент снова `-00000000`, и завершение старой
  склейки затёрло бы его старыми данными. Поэтому: (1) под замком выгрузки зоны — снимок
  поколения и объектов; (2) без замка — копирование частей (FLUSH и RESET не ждут; удалённый RESET
  объект — 404 и отмена); (3) снова под замком: поколение то же и объекты зоны начинаются со
  снимка → `CompleteMultipartUpload`, карта зоны — база плюс новые фрагменты; иначе
  `AbortMultipartUpload`; (4) под тем же замком — удаление склеенных фрагментов: без замка RESET
  и новая запись успели бы положить новый фрагмент под тем же ключом, и удаление стёрло бы его.
  Чтение, которое как раз шло по удалённому фрагменту, получает 404 и строит план заново. RESET
  увеличивает поколение в начале, а не в конце: склейка не завершится и после неудачного RESET.
- **Восстановление:** из листинга для каждой зоны от смещения 0 берётся объект, покрывающий
  текущий конец, дальше всех; указатель записи — конец покрытия. Остальное удаляется: объекты
  внутри покрытия — недоудалённые склеенные фрагменты, объекты за разрывом недостижимы (оставить
  нельзя: зона, дорастя до них, вплела бы их в данные). Нет фрагмента `-00000000` — зона EMPTY,
  всё её удаляется (ниже). Незавершённые склейки (`ListMultipartUploads` под префиксом диска)
  прерываются.

### RESET и частичное удаление

Удаление не атомарно: `DeleteObjects` может удалить часть ключей в любом порядке, демон может
упасть между запросами. Опасно не само недоудаление, а остаток, который переживёт RESET и
соединится с новыми данными зоны: фрагмент за новым концом `cover()` вплетёт в данные, а метка
FINISH сделает новую зону FULL. Кроме того, непустая зона, которую btrfs считает свободной,
для btrfs аномалия: перед выделением она сбрасывает такую зону ещё раз
(`btrfs_ensure_empty_zones`) с `WARN_ON_ONCE` «Free regions should be empty». Решение
пользователя — промежуточных состояний не допускать:

- **Порядок:** сначала объект в начале зоны (`<зона>-00000000` или объект зоны `PATCH`), и только
  после успеха — остальное: прочие фрагменты, `.finished`, `.meta` (в `SEGMENTS` по листингу
  префикса зоны, он идёт параллельно с первым удалением; в `PATCH` метка — по флагу, §3.3).
  RESET_ALL — так же, двумя фазами.
- **Старт:** нет данных в начале зоны — зона EMPTY, остальное её удаляется до запуска устройства.
  Поэтому прерванный RESET оставляет зону либо нетронутой (RESET не произошёл), либо EMPTY.
- **Неудачный RESET** (ошибка S3 после повторов): зона помечается испорченной — буфер
  сброшен, чтение, запись, FINISH и выгрузка — `EIO`, склейка не завершится (поколение уже
  другое). Состояние и указатель в отчёте прежние: btrfs видит зону непустой и перед
  использованием повторит RESET (при ошибке сброса она не помечает зону пустой). Успешный RESET
  возвращает зону в строй. Неудачный RESET_ALL портит только зоны, где что-то было: пустую зону
  ядро сбрасывать не станет, а удалять у неё нечего.
- Флаги меток в памяти — «возможно, есть»: метка помечается до своего `PUT`.
- Цена: зона из нескольких объектов — два запроса подряд (как и раньше: листинг и удаление);
  ядро присылает RESET строго по одному, поэтому их темп ≈ 1 / (2 задержки S3). Фоновое
  удаление с подтверждением RESET сразу — §13.
- Каждая выгрузка ≥ 4 КиБ ⇒ не больше 4096 дозаписей в объект.
- **Завершённые зоны** — FULL и CLOSED (в том числе неполные) — выгружаются сразу, не дожидаясь
  FLUSH и лимита (решение пользователя): в FULL больше не пишут, CLOSED btrfs закрыла;
  зона, набранная в RAM целиком, уходит одним `PUT`.
- **Лимит грязных данных** (`dirty_limit_bytes`, 256 МиБ): сверх него — фоновая выгрузка и
  открытых зон, самые большие буферы первыми. Новая выгрузка начинается сразу по окончании
  прежней. При 2 × лимита новые записи ждут (защита от OOM при недоступном S3): запрос сначала
  атомарно резервирует место под свой размер и только потом копирует данные из ядра, так что
  ждущий запрос данных не держит, а освободившееся место достаётся только тем, кому его хватает;
  при пустых буферах проходит любой запрос.
- **Общий предел выгрузок** (§6.1) — на все причины вместе (FLUSH, FUA, фон, FINISH): лишние
  ждут свободного места.
- **Остановка** (`umount`, `detach`, SIGTERM): данные, не подтверждённые FLUSH/FUA, **не
  досылаются** — как кеш диска при пропадании питания (решение пользователя); в лог — объём.
  После `umount` btrfs сама шлёт FLUSH, отбрасывать нечего. `create` после mkfs сбрасывает
  всё явно.

## 6. Чтение и подстройка под связь с S3

### 6.1. Подстройка

Решение пользователя: админ меряет связь командой `btrs3fs measure` и передаёт результат
флагами `mount`/`run`; демон вычисляет из него свои параметры и пишет в журнал, что вычислил
и что выставил. Флаги — свойство машины, не диска (не `disk.json`). Без флагов — значения,
измеренные на ВМ в Yandex Cloud, с предупреждением в журнале.

Характеристики связи:

| Флаг | Что | Как меряет `measure` |
|---|---|---|
| `--s3-latency` L | задержка ответа | медиана 64 GET по 4 КиБ, по 16 одновременно — по разным соединениям (последовательно по одному соединению давали то 15, то 37 мс) |
| `--s3-read-stream` R₁ | скорость одного GET после первого байта | пара подряд: GET 4 КиБ и GET 16 МиБ, разница байт / разница времени (задержка соединения сокращается); медиана из 5 |
| `--s3-read-total` Rₘ | суммарная скорость чтения | GET по 4 МиБ, 64 одновременно, 5 с |
| `--s3-write-stream` W₁ | скорость одного PUT после первого байта | то же парой PUT 4 КиБ и PUT 16 МиБ |
| `--s3-write-total` Wₘ | суммарная скорость записи | PUT по 4 МиБ, 64 одновременно, 5 с |

`measure` пишет временные объекты под `<prefix>/measure-<случайное>/` и удаляет их.

Правила (обоснование — замеры §12):

| Параметр | Правило | Облако | Ноутбук |
|---|---|---|---|
| Единица передачи U | L × R₁, до степени двойки, 128 КиБ … 4 МиБ: докачать U стоит столько же, сколько лишний запрос; случайное чтение не дороже двух задержек | 2 МиБ | 128 КиБ |
| Окно чтения с запасом | U | 2 МиБ | 128 КиБ |
| Часть GET крупного чтения | U | 2 МиБ | 128 КиБ |
| Окно упреждения btrfs (`bdi/read_ahead_kb`) | 4 × L × Rₘ, до степени двойки, 4 … 256 МиБ: столько байт должно быть в пути, коэффициент 4 подобран по замеру | 64 МиБ | 4 МиБ |
| Одновременных выгрузок (всего) | Wₘ / скорость одной выгрузки зоны (16 МиБ / (L + 16 МиБ / W₁)), 4 … 64 | 21–36 | 4–16 |

- Окно упреждения принадлежит смонтированной ФС, а не устройству: демон раз в секунду ищет
  свою ФС (`/sys/fs/btrfs/*/devices/ublkbN`) и выставляет `bdi/read_ahead_kb` — так и при
  `mount`, и при монтировании через fstab.
- `--read-cache` (64 МиБ) — бюджет RAM, а не характеристика связи; задаётся напрямую.
- Временное устройство `create` работает без подстройки (mkfs почти не читает).

### 6.2. Чтение с запасом

- Чтение выгруженных данных меньше окна забирает одним GET всё окно, выровненное от начала
  зоны, и кладёт его в LRU. Соседние мелкие чтения — из кеша; чтение размером с окно и больше
  идёт мимо кеша.
- Кешируются только окна, целиком лежащие в `[0, flushed)`: эти данные не меняются до RESET.
  Ключ кеша — `(зона, поколение, окно)`; RESET увеличивает поколение, поэтому старое окно
  новой зоне не отдаётся, даже если GET закончился после RESET.
- Одновременные чтения одного окна делят один GET (`tokio::sync::OnceCell`); неудачный GET
  оставляет окно пустым.
- **Крупные чтения.** Упреждение ядра не распараллеливает само: окно — один запрос,
  следующее окно заказывается по метке `PG_readahead`. Окно больше `max_sectors_kb` (зона)
  режется ядром на одновременные запросы, а каждый запрос из S3 больше U демон делит на части
  по U и забирает одновременными GET: окно 64 МиБ — 4 запроса — 32 GET.

## 7. Многопоточность

```
 0 ─────────── flushed ──────────── data_end ──── wp ──── zone_size
 │ в S3, неизменно │ в RAM, ещё не в S3 │ нули (после FINISH wp = зона)
```

```rust
struct ZoneState {            // std::sync::Mutex на зону
    cond: Cond, wp: u64, data_end: u64, flushed: u64,
    chunks: VecDeque<Bytes>,  // данные [flushed, data_end), по куску на запрос
    object: bool,             // объект есть в S3
    generation: u64,          // растёт при RESET, ключ кеша чтения
}
struct Zone { state: Mutex<ZoneState>, upload: tokio::sync::Mutex<()> }
```

1. Байты уходят из RAM **только после** подтверждения S3; ошибка выгрузки — `flushed` не
   двигается, следующий FLUSH повторяет тот же диапазон.
2. Под `state` нет сетевого ввода-вывода: снимок (клоны `Bytes`), отпустить, идти в сеть.
3. Порядок замков: `upload`, потом `state`. `RESET_ALL` берёт все `upload` по порядку зон —
   больше никто не держит двух сразу. Фоновые циклы (выгрузка, склейка, метки `.meta`) внутри
   себя ничего не ждут, кроме своих задач и пробуждений: задачи в `FuturesUnordered` идут, только
   пока их опрашивают, а держат замки зон. Метки ставит отдельный цикл рядом со склейкой
   (`join!` в одной задаче) — иначе метка, ждущая замок зоны, который держит неопрашиваемая
   склейка, вешала бы и склейку, и FLUSH/RESET этой зоны. Пауза после ошибки — момент «не
   запускать новое до», а не `sleep` в цикле.
4. Запись подтверждается после попадания в `chunks` под замком, FLUSH читает под тем же
   замком ⇒ видит все подтверждённые записи из любой очереди.
5. Обычные `WRITE` в зону ядро отдаёт по одной (zone write plugging), проверка указателя —
   страховка; `ZONE_APPEND` идут параллельно и упорядочиваются замком зоны.

**Копирование.** Зоны в ublk требуют `UBLK_F_USER_COPY`: данные копируются `pread`/`pwritev`
на `/dev/ublkcN` — одно копирование на запись и на чтение. Zero-copy невозможен и не нужен:
запись подтверждается до FLUSH (страницы возвращаются ядру), TLS всё равно копирует, а
непривилегированному ublk он запрещён. Буфер зоны — список `Bytes`, тело PATCH идёт потоком
без склейки; ответ на чтение — `pwritev` пачками по `IOV_MAX`.

## 8. S3-клиент

| Событие | Запрос |
|---|---|
| Первая / следующие выгрузки зоны | `PUT` / `PATCH` + `Content-Range`, `PUT ?append&position=` или `PUT` нового фрагмента (§5) |
| Склейка фрагментов (`SEGMENTS`) | `CreateMultipartUpload`, `UploadPartCopy` × N, `CompleteMultipartUpload` / `AbortMultipartUpload`, `DeleteObjects`; при старте `ListMultipartUploads` |
| Чтение | `GET` + `Range` |
| FINISH | `PUT` пустой метки `<зона>.finished` |
| `ZONE_RESET` | `DELETE` начала зоны, затем остальное (`SEGMENTS`: листинг + `DeleteObjects`; `PATCH`: `DELETE` метки) |
| `ZONE_RESET_ALL`, `destroy` | `DeleteObjects` (`POST ?delete`): до 1000 ключей, до 4 запросов параллельно; `destroy` удаляет `disk.json` последним |
| Старт | `GET disk.json`, `ListObjectsV2` |
| `create` | `ListObjectsV2` (префикс пуст?), `PUT disk.json`, выгрузка после mkfs |

- Подпись SigV4 с `UNSIGNED-PAYLOAD`.
- `DeleteObjects` — режим `Quiet` (в ответе только сбои), отсутствующий ключ — не ошибка,
  с `x-amz-checksum-crc32c` списка ключей: стандарт S3 требует контрольную сумму тела (Selectel
  проверяет, Яндекс принимает), CRC32C — самая быстрая из допустимых (одна инструкция процессора
  на 8 байт; крейт `crc32c`). Сбой части ключей с `InternalError`/`SlowDown`/
  `ServiceUnavailable` — повтор пакета, прочие коды — ошибка.
- Транспорт: только HTTP/1.1, пул соединений (по соединению на запрос в работе,
  переиспользуются; простой — 90 с), `TCP_NODELAY`, TCP keepalive 30 с, connect 10 с,
  чтение 60 с. Прокси — `--proxy` (переменные окружения сбрасывает `sudo`).
- Повторы: сеть, таймауты, 5xx, 429, 408, 400 без кода S3 (§11), а также коды S3 о передаче,
  а не о запросе: `RequestTimeout`, `IncompleteBody` (400), `RequestTimeTooSkewed` (403 — часы
  после сна, пока их не поправит NTP) — с паузой `retry_initial_delay_ms ×
  retry_backoff_factor^n` в пределах `retry_timeout_seconds`; прочие 4xx — сразу ошибка.
  Бюджет исчерпан ⇒ `EIO` ядру, данные остаются в RAM.

## 9. Процесс и команды

### 9.1. Устройство процесса

```
 ядро ─ublk─► nr_queues потоков (libublk: свой io_uring + `UblkRuntime`)
                │ WRITE/APPEND → RAM, ответ сразу; READ из RAM/нулей → ответ сразу
                │ READ из S3, FLUSH, FUA ──► пул tokio (reqwest → S3)
                ◄── eventfd «готово» ───────┘
```

Поток очереди спит в io_uring, поэтому tokio будит его через eventfd, зарегистрированный в
io_uring (`libublk::ops::submit_sqe`). Состояние зон — общий `Arc<Engine>`.

### 9.2. Команды

Справочник — `manual.md` §5. Устройство:

- `create`: проверяет, что префикс пуст, пишет `disk.json`, поднимает временное устройство,
  в колбэке готовности — `mkfs.btrfs -O zoned -d single -m single`, явная выгрузка, удаление устройства; при
  ошибке удаляет созданное.
- `mount`: `fork()` до создания потоков; потомок — `setsid`, `chdir /`, stdio на `/dev/null`
  (stderr — если нет `--log-to-stderr`), готовность родителю по pipe: `READY <bdev> <порт>`
  или `ERROR …`. Родитель — `mount -t btrfs -o nosuid,nodev,noatime,lazytime,commit=300[,…]`, при ошибке
  SIGTERM потомку. Опции монтирования — решение пользователя (`manual.md` §7); `nosuid,nodev` —
  потому что образ ФС приходит из бакета: кто может писать в бакет (или подменить ответы S3),
  иначе подложил бы setuid-файл или узел устройства и получил root на машине.
- `umount`: устройство по точке из `/proc/self/mountinfo` → `umount` → `detach`.
- `detach`: отказ, если `/dev/ublkbN` открыт (`O_EXCL`); иначе SIGTERM серверу и ожидание.
  Сервера нет или устройство в `FAIL_IO` — `DEL_DEV`. `--force` — SIGKILL без проверок.
- После создания устройства и до сигнала готовности демон пишет sysfs своего устройства:
  `wbt_lat_usec = 0`, `max_sectors_kb` (§2).

### 9.3. Логи и статистика

- Логи: фильтр `--log-level` (синтаксис env_logger, по умолчанию `info,libublk=warn`) →
  journald (`systemd-journal-logger`), иначе syslog `/dev/log`; `--log-to-stderr` —
  `env_logger`. В файлы — никогда. Трассировка запросов ядра (`requests=trace`) идёт только в
  stderr. Сообщения — на английском.
- Статистика: глобальный `STATS` на relaxed-атомиках (процесс — один диск), веб-страница
  `tiny_http` в своём потоке на `127.0.0.1:9470+N` (`--stats-port`, `--no-stats`);
  `src/stats.html` встроена через `include_str!`, раз в секунду берёт `/stats.json`. Сервер
  работает от root и умеет действия (`POST`), поэтому принимает только `Host` — loopback-имя
  (`127.0.0.1`, `localhost`, `[::1]`, любой порт — SSH-туннель его меняет) и `Origin`, если он
  есть, — тоже loopback: иначе чужой сайт в браузере пользователя запускал бы действия формой
  (POST без предварительного запроса), а через DNS rebinding и читал бы статистику. curl
  `Origin` не шлёт.
- Страница (редизайн по решению пользователя) отвечает на вопрос «всё ли в порядке и где
  затор». Разделы в левой панели: «Обзор» — предупреждения, конвейер записи (ядро → RAM → S3) и чтения
  (зеркально: ядро ← кеш ← S3, S3 под S3) со скоростями, заполнением RAM, временем до разгрузки, графики за 5 минут;
  «Зоны» — карта всех зон (клетка на зону: состояние, раздробленность, данные в RAM; подробности
  при наведении); «btrfs»; «Детали» — гистограммы и счётчики. Предупреждения считает демон
  (`alerts`: запись ждёт места в RAM, свежие ошибки выгрузки/чтения/склейки, ошибки
  ввода-вывода ядру, ФС read-only), страница только показывает; последние ошибки — текст и
  давность (`last_errors`); ждущие места запросы записи — `writes_waiting`. Карта зон —
  `/zones.json` (состояние, указатель записи, объектов S3, байт в RAM на зону), страница берёт
  его раз в 3 с, пока открыта вкладка.
- Гистограммы без зашитых границ (решение пользователя): корзины задаёт шкала, демон считает и
  отдаёт готовые корзины `[lo, hi]`, число, сумму, среднее и p50/p90/p99 (верхняя граница
  корзины); страница только печатает. Шкалы: размеры — степени двойки от блока (4 КиБ) до
  размера зоны (больше запроса не бывает), показываются все корзины этого диапазона (размеры
  запросов ядра READ, WRITE, ZONE_APPEND; выгрузок; GET); время —
  ряд 1-2-5 мс без верхней границы, количества (зон на FLUSH, фрагментов на склейку) — 0, затем
  степени двойки; у них показ от первой до последней непустой корзины.
- Зоны: пустые, открытые, закрытые, полные; недозаполненные (данные есть, но меньше зоны: открытые,
  закрытые и FULL после FINISH раньше конца); раздробленные (больше одного объекта, в том числе
  FULL, ещё не склеенные), фрагментов всего и больше всего в одной зоне.
- Склейка (`SEGMENTS`): в очереди (срочных — FULL) и в работе, выполнено, склеено фрагментов и
  байт (копирование на сервере), отменено (зона изменилась), ошибки; время склейки и фрагментов
  на склейку — гистограммы.
- Действие `POST /compact` (кнопка в карточке зон, только `SEGMENTS`; решение пользователя):
  все раздробленные зоны — в очередь склейки как срочные, ответ — сколько поставлено. Только
  `POST`, чтобы склейку не запускали переходы по ссылкам и предзагрузка браузера.
- Действие `POST /flush` (кнопка в карточке буферов; решение пользователя): выгрузка всех
  буферов в фоне, как FLUSH (причина «upload button»), ответ — сколько зон и байт. Транзакцию
  btrfs не фиксирует: файлы переживут аварию только после её фиксации (`sync`, `commit=`).
- Вкладка «btrfs» (решение пользователя; без запуска внешних программ — только sysfs, ioctl и
  системные вызовы): `/btrfs.json`, страница берёт его, пока вкладка открыта. ФС демона —
  `/sys/fs/btrfs/<fsid>/devices/ublkbN`, точка монтирования и `ro` — `/proc/self/mountinfo`.
  Показ: метка, fsid, поколение, rw/ro, фиксации (`commit_stats`), глобальный резерв, места по
  типам (`allocation/*`: выделено, занято, zone unusable, pinned/reserved/may_use/readonly,
  на диске, порог и счётчики reclaim), ошибки устройства (`devinfo/*/error_stats`), текущая
  исключительная операция и прогресс balance (`BTRFS_IOC_BALANCE_PROGRESS`).
  Действия `POST /balance` — `BTRFS_IOC_BALANCE_V2` с фильтром данных `usage=0` (удаление пустых
  групп, как `btrfs balance start -dusage=0`), `POST /syncfs` — `syncfs()` на точке монтирования.
  Оба долгие: идут в отдельном потоке, одновременно — одно; страница видит, что идёт и чем
  кончилось последнее.

### 9.4. Смерть демона

Без флагов восстановления ядро при смерти сервера удаляет диск: `del_gendisk()` под
`ub->mutex` вызывает `sync_filesystem()` смонтированной ФС; если её writeback завис —
навсегда, а за ним (через глобальный `ublk_ctl_mutex`) все команды ublk на машине
(`bugreports/`).

С `UBLK_F_USER_RECOVERY | UBLK_F_USER_RECOVERY_FAIL_IO` диск остаётся в
`UBLK_S_DEV_FAIL_IO` и сразу отвечает `EIO`; ФС отключается, `umount` проходит, `detach`
удаляет устройство. Само восстановление не используется: кеш записи только в RAM, новый
сервер поднял бы указатели зон по S3 — позади того, что видит ФС. Штатная остановка не
меняется.

`libublk` 0.4.8 этот флаг не пропускает; правка принята в апстрим (`main`, будущая 0.5), на
crates.io её ещё нет. Поэтому зависимость — git с закреплённым `rev` в `Cargo.toml`; после
выхода 0.5 на crates.io — перейти на версию оттуда.

## 10. Права и окружение

- **Ядро ≥ 6.13.** Нужны возможности ublk `USER_COPY` (6.5), `ZONED` (6.6) и
  `USER_RECOVERY_FAIL_IO` (6.13, история `include/uapi/linux/ublk_cmd.h`). Демон проверяет их
  через `GET_FEATURES` и без любой из них завершается с ошибкой — обходных путей нет (решение
  пользователя). Номер версии ядра не проверяем: известные ошибки старых ядер (§11) по
  возможностям не видны, а ядра дистрибутивов получают исправления при старом номере (решение
  пользователя).
- Демону нужен root (`CAP_SYS_ADMIN`). Рабочая система — демон через systemd unit.
- Разработка: правила sudoers — `NOPASSWD` на `<repo>/target/debug/btrs3fs` (кто может его
  пересобрать, фактически root — решение пользователя; отвергнуты ВМ, ручная установка в
  `/usr/local/bin`, привилегированный помощник) и ровно `chown <user> /mnt/btrs3fs` (корень
  новой ФС принадлежит root, `mkfs.btrfs --rootdir` с zoned несовместим).
- Группа `btrs3fs` — чтение и запись `/dev/ublkbN` (udev-правило) без root; строка fstab
  `/dev/ublkb0 /mnt/btrs3fs btrfs noauto,user`.
- `sudo` сбрасывает окружение: уровень логов и прокси — флаги, не переменные.
- `setup-permissions.sh` (запускает пользователь): `install` — пакеты для работы и права
  (sudoers, группа, udev, загрузка `ublk_drv`, fstab); `uninstall` — откат прав;
  `build-deps` — сборка (`rust`, `cargo`, `clippy`, `rustfmt`, `gcc`, `clang-devel`,
  `kernel-headers`, `glibc-devel`, `git`); `diag-tools` — `fio`, `blktrace`, `sysstat`,
  `strace`, `gdb`, `perf`, `jq`, `awscli2`, `bpftrace`, `drgn`. Пакеты для работы:
  `kernel-modules-core`, `systemd-udev`, `shadow-utils`, `sudo`, `util-linux`, `btrfs-progs`,
  `ca-certificates`, `coreutils` (`basenc` для правила udev).
- Окружение разработки: Fedora 44, ядро 7.2, Rust 1.99, btrfs-progs 7.1.

## 11. Проверенные факты

**Ядро и ublk**
- Непривилегированному ublk запрещены `USER_COPY`/`ZERO_COPY`/`AUTO_BUF_REG`, а зонам нужен
  один из них ⇒ только root.
- Обычные `WRITE` в зону ядро сериализует (zone write plugging); нативный `ZONE_APPEND` —
  нет.
- `REQ_META` доходит до сервера как `UBLK_IO_F_META`. btrfs ставит его на все чтения и записи
  метаданных (суперблок — `META|FUA`); данные — `ZONE_APPEND` без флага, в том числе перенос
  при reclaim. Без флага метаданные пишет mkfs и читают пробы udev/blkid; btrfs читает
  суперблок без флага (отчёт в `bugreports/`). Надёжное правило: `ZONE_APPEND` → данные,
  запрос с флагом → метаданные, запрос без флага тип не задаёт.
- `libublk` 0.5 (`main` 5dff30d) на ядре 7.2: create, mount, запись, umount, повторный mount —
  данные целы; `detach --force` при смонтированной ФС — устройство остаётся, прямое чтение
  получает `EIO`, `umount` убирает устройство, после повторного mount сброшенное цело.

- Версии ядра (по исходникам на git.kernel.org): `queue/wbt_lat_usec`, `queue/max_sectors_kb` —
  с 4.10 и раньше; параметры ublk `io_opt_shift`, `UBLK_IO_F_META` — 6.0; `GET_FEATURES`,
  `USER_COPY` — 6.5; `ZONED` — 6.6; zone write plugging — 6.10; `USER_RECOVERY_FAIL_IO` и
  `max_hw_zone_append_sectors` — 6.13; btrfs `bg_reclaim_threshold` общий — 5.13, по группам —
  5.19, `dynamic_reclaim`, `periodic_reclaim`, `reclaim_count` — 6.12; `queue/zoned_qd1_writes` —
  7.1 (мы его не используем).
- Важные для нас исправления после 6.13 (ublk, зонированный блочный уровень, btrfs zoned):
  отмена и восстановление ublk (6.15–6.16, `reset per-IO canceled flag` — 7.1);
  `blk_zone_reset_all_bio_endio` NULL (6.19); удаление плагов записи зоны (7.1); btrfs zoned —
  активация зон и резерв под перенос данных (6.17), указатель записи DUP после удаления
  экстентов (7.0), потеря ошибки ввода-вывода при разбиении записи (7.1), взаимоблокировка
  writeback метаданных и фиксации транзакции (7.2). Почти всё портировано в 6.18.y (проверено
  на 6.18.58); не портированы: потеря ошибки ввода-вывода (btrfs, 7.1), use-after-free в
  `ublk_cancel_cmd` (7.1), флаг отмены без диска (ublk, 7.2), взаимоблокировка при ошибке
  перепроверки зон (7.2). Ветки 6.13–6.17 закрыты и этих исправлений не получат.

**btrfs**
- Предел активных зон: `min_not_zero(max_active, max_open)`, если 0 — `min(зон/4, 128)`, не
  меньше 8; лишние зоны btrfs закрывает FINISH. При DUP-метаданных 6 активных зон в резерве
  под метаданные/system: с лимитом устройства 8 btrfs навсегда виснет на первой записи данных
  (`bugreports/`). Если активных зон при монтировании больше лимита, а устройство лимит
  сообщает — отказ монтирования; без лимита btrfs учёт отключает.
- Идентификация (ядро 7.2, systemd-udev Fedora 44, util-linux 2.41): ublk не передаёт ни
  модель, ни серийный номер, у устройства нет `/sys/block/…/device/`. `lsblk` берёт `MODEL`,
  `SERIAL`, `WWN`, `REV` из свойств udev (`ID_MODEL_ENC`/`ID_MODEL`, `ID_SERIAL_SHORT`, `ID_WWN`,
  `ID_REVISION`), `VENDOR`/`TRAN`/`HCTL` — только из sysfs. Пределы длины: метка btrfs —
  255 байт (`mkfs.btrfs`); имя ссылки udev — 255 байт (`NAME_MAX`), то есть серийный номер в
  `btrs3fs-<serial>` — до 247 символов, длиннее udev ссылку не создаёт. У настоящих дисков
  серийный номер — 20 символов (ATA, NVMe, virtio-blk).
- Синтетическое событие (`/sys/…/uevent`): `<действие> <uuid> KEY=VALUE …`; в ключах и
  значениях ядро принимает только латинские буквы и цифры (`- _ . / :` и прочие — `EINVAL`);
  все переменные события — до 2 КиБ, при переполнении ядро печатает WARNING с трассировкой.
  udev видит их как `SYNTH_ARG_KEY`; правило может склеить их (`ENV{X}="$env{X}-…"`) и
  сохранить на следующие события через `IMPORT{db}` — проверено на ВМ.
- Два диска btrs3fs (разные префиксы) в одной ФС: `btrfs device add` работает, `balance
  -mconvert=raid1 -sconvert=raid1` проходит, scrub чист. Данные в RAID1 — отказ «zoned: data
  raid1 needs raid-stripe-tree»: в zoned нужен `raid-stripe-tree` (mkfs), а он только при
  `CONFIG_BTRFS_EXPERIMENTAL`, выключенном в ядре Fedora 7.2 и в btrfs-progs 7.1.
- Reclaim (`fs/btrfs/{space-info,block-group,zoned}.c`): общий `bg_reclaim_threshold` (75) в
  zoned — «распределено ≥ N %», 0 выключает переработку; статический порог по группам — 75,
  `dynamic_reclaim` целит в 10 нераспределённых зон. Рекомендация — `manual.md` §13.
- На диске 1 ГиБ при заполнении ~55 % с reclaim btrfs может прервать транзакцию из-за
  нехватки места под метаданные (`-28`) — для проверок брать диск больше.

**Почему размер диска не меняется на ходу** (исходники 7.2, 2026-10-26; решение пользователя —
не делать)
1. **Ядро, блочный уровень и ublk.** `UBLK_U_CMD_UPDATE_SIZE` (`UBLK_F_UPDATE_SIZE`) лишь меняет
   ёмкость (`ublk_ctrl_set_size()` → `set_capacity_and_notify()`) и не перепроверяет зоны: число
   зон и служебные структуры по зонам (`disk->nr_zones`, плаги записи) строятся один раз при
   запуске устройства (`blk_revalidate_disk_zones()` в `ublk_revalidate_disk_zones()`). У
   зонированного диска после такой команды ёмкость новая, а зон — прежнее число.
2. **btrfs в зонированном режиме.** Карты зон устройства (`zone_info->nr_zones`, `seq_zones`,
   `empty_zones`, `active_zones`) выделяются при монтировании по размеру устройства в тот момент
   (`btrfs_get_dev_zone_info()`, `zoned.c`). `btrfs_grow_device()` (`BTRFS_IOC_RESIZE`) про зоны
   ничего не знает, а `btrfs_dev_is_sequential()` читает битовую карту без проверки границ:
   группа блоков за прежним концом устройства — обращение за пределы выделенной памяти ядра.

Обе причины снимаются только перемонтированием (новый запуск устройства и новое монтирование)
или правкой ядра (ublk: перепроверка зон при `UPDATE_SIZE`; btrfs: перевыделение карт зон при
росте устройства).

**Yandex Object Storage**
- PATCH: несуществующий объект — `404`; начало за концом — `416` (дыр нет); повтор —
  идемпотентен; перекрытие с продлением — `200`. 5228 дозаписей по 4 КиБ подряд — без
  ошибок (лимит не найден).
- Задержка PATCH: объект, выросший из дозаписей, до ~16 МБ — 0,2–0,6 с, после ~20 МБ —
  9–30 с; созданный одним PUT — 0,5–2 с. `CopyObject` в другой ключ линеаризует объект, но
  через ~5 МБ новых дозаписей всё возвращается.
- `UNSIGNED-PAYLOAD` принимается; переданный хеш тела сервер проверяет.
- Условные запросы (с ноутбука, `curl --aws-sigv4`): `PUT` с `If-None-Match: *` на
  существующий объект — `412 PreconditionFailed`, на новый — `200`; `If-Match` с чужим ETag на
  `PUT` и `DELETE` — `412`, с верным — выполняется. 10 одновременных `PUT` с `If-None-Match: *`
  на новый объект, 3 раза: ровно один `200`, девять `412`, в объекте — данные победителя.
- Теги приходят в `ListObjectsV2`; `x-amz-tagging` при PUT принимается, при PATCH — молча
  игнорируется (как и `x-amz-meta-*`).
- `DeleteObjects` принимается и без контрольной суммы, и с `x-amz-checksum-crc32c`.
- HTTP/2 поддерживается, но при многих потоках в соединении отвечает `REFUSED_STREAM`.

**Selectel** (`s3.ru-7.storage.selcloud.ru`, 2026-10-26)
- `PATCH` — `405`. `PutObjectTagging` — `NotImplemented`; `x-amz-tagging` при PUT принимается,
  но теги не сохраняются.
- Append Object из Ceph RGW (`PUT ?append&position=N`) отвечает `200`, но игнорирует
  параметры и **перезаписывает объект целиком**, неверная позиция — тоже `200`.
- Multipart: `UploadPartCopy` (и с `x-amz-copy-source-range`) работает в тот же ключ; части
  меньше 5 МиБ разрешены (склейка 64 × 16 КиБ — 0,9 с, 1 МиБ + 255 × 4 КиБ — 1,6 с, содержимое
  верное). Яндекс те же склейки отвергает: `EntityTooSmall` (части ≥ 5 МиБ, как AWS).
- LIST сразу после `PUT`/`DELETE` — 100 из 100 актуальны (Яндекс — тоже).
- `DeleteObjects` без контрольной суммы — отказ (`Content-MD5 or Amz-Content-Checksum`);
  `x-amz-checksum-crc32c` принимается.
- `POST`/`PUT` без тела требуют `Content-Length: 0` (иначе `411`).
- Повтор запроса к ключу, пока прошлый (брошенный нами по таймауту) ещё числится у сервера, —
  `409 OperationAborted` «A conflicting conditional operation is currently in progress … Try
  again»: повторяется как временная ошибка. С ноутбука при 30 параллельных выгрузках по 16 МиБ
  (настройки по умолчанию — облако) ни одна не завершилась: `408 Request Time-out` («didn't send
  a complete request in time») и таймауты соединения; канал ~24 МиБ/с на всех — меньше 1 МиБ/с
  на выгрузку. Вне облака `--s3-*` из `measure` обязательны.
- При смене маршрута на ходу (VPN → мимо него) балансировщик ответил на два оборванных запроса
  HTML `400 Bad request — Your browser sent an invalid request`, без XML-кода S3. Ответ считался
  фатальным; одна такая выгрузка была частью FLUSH → `EIO` → btrfs прервала транзакцию и стала
  read-only. Теперь 400 без `<Code>` повторяется; 400 с кодом S3 — ошибка, кроме кодов о передаче (§8).
- С ноутбука: задержка 38 мс, чтение ~33 МиБ/с, запись ~24 МиБ/с (упор в канал). `PUT` 16 КиБ —
  p50 77 мс (дозапись multipart была 261 мс), Яндекс: `PUT` 89 мс, `PATCH` 155 мс.

## 13. Отложено

| Что | Набросок |
|---|---|
| Адаптивное окно чтения | Окно растёт при последовательных промахах в зоне и заранее подкачивает следующее. |
| Окно упреждения btrfs больше 4 МиБ | `mount` пишет `bdi/read_ahead_kb` после монтирования: те же параллельные части, но крупнее — меньше GET. В режиме `run` + fstab демон момента монтирования не знает. |
| Отдельная политика для метаданных | По флагу `UBLK_IO_F_META` (§11): своё окно и кеш; тег типа зоны при `PUT`. |
| Изменение размера диска | Решение пользователя: не делать. На ходу невозможно (§11: ublk не перепроверяет зоны, btrfs не перевыделяет карты зон). Через перемонтирование: увеличение — `disk.json` → перемонтирование → `BTRFS_IOC_RESIZE max`; уменьшение — `BTRFS_IOC_RESIZE` → `umount` → нет объектов за границей → `disk.json` → `mount`. |
| Блокировка от двух машин | Условный `PUT <prefix>/lock` (`If-None-Match: *`) с id владельца, снятие при остановке. |
| Фоновое удаление при RESET | Подтверждать RESET сразу, ключи — в очередь, `DeleteObjects` пачками до 1000; FLUSH ждёт опустошения очереди, первая запись в зону — удаления её старых объектов. Сотни RESET/с вместо ≈ 10 (§5). Решение пользователя: пока не делать. |
| Прозрачный перезапуск демона | Только с журналом записей на локальном диске; без него перезапуск теряет данные после FLUSH и сдвигает указатели зон. |

**Решения по умолчанию, не подтверждённые пользователем явно:** порог 2 × `dirty_limit`;
имена зон в нижнем регистре; `detach` отказывает при смонтированном устройстве; `destroy`
требует `--yes`; `nr_queues`/`queue_depth` в `disk.json` (`--queues` переопределяет);
`queue_depth` 128, `retry_initial_delay_ms` 100, `retry_backoff_factor` 2.0.
