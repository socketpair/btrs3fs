# btrs3fs — руководство пользователя

btrs3fs превращает префикс в S3-бакете в диск с файловой системой btrfs. Под капотом —
зонированное блочное устройство Linux (ublk): каждая зона диска — отдельный объект в бакете,
btrfs работает с ним в zoned-режиме. Устройство и решения — `SPEC.md`.

## 1. Требования

- **Linux ≥ 6.13** с `ublk_drv` (`CONFIG_BLK_DEV_UBLK`) и `CONFIG_BLK_DEV_ZONED`; проверено на 7.2.
  На более старом ядре btrs3fs не запускается и называет недостающие возможности ublk.
- root для `create`, `mount`, `umount`, `run`, `detach`: зонированное ublk-устройство ядро
  разрешает только привилегированному процессу.
- S3 с **выключенным версионированием**: Yandex Object Storage (дозапись его `PATCH`), Ceph RGW
  (Append Object) или другой S3, умеющий склеивать на сервере мелкие части (`UploadPartCopy`;
  проверен Selectel). AWS S3 не подходит. Способ
  дозаписи `create` выбирает сам.
- `btrfs-progs`, `util-linux`, сертификаты CA; пакеты Fedora — `RUNTIME_PACKAGES` в
  `setup-permissions.sh`.

## 2. Установка

```bash
cargo build --release
sudo install -m 755 target/release/btrs3fs /usr/local/bin/
sudo modprobe ublk_drv
echo ublk_drv | sudo tee /etc/modules-load.d/btrs3fs-ublk.conf   # загрузка при старте
```

Для сборки нужны Rust и `BUILD_PACKAGES` из `setup-permissions.sh` (`sudo
./setup-permissions.sh build-deps` на Fedora).

С правилом udev из `sudo ./setup-permissions.sh install` диск виден в `lsblk` с
`MODEL` = `btrs3fs`, `SERIAL` = `<бакет>/<префикс>`, `REV` = версия btrs3fs и ссылкой
`/dev/disk/by-id/btrs3fs-<бакет>-<префикс>` (`/` и прочие символы, недопустимые в имени, —
`-`). Без правила эти поля пусты, работе диска это не мешает.

## 3. Файл реквизитов

YAML (можно с комментариями; JSON с теми же ключами тоже подходит), путь — флаг `--creds`;
реквизиты нигде не печатаются. Права `0600`, владелец root. Пример — `examples/creds.yaml`:

```yaml
endpoint: https://storage.yandexcloud.net
region: ru-central1
bucket: my-bucket
access_key: ...
secret_key: ...
```

`endpoint` — только `https://хост[:порт]`, без пути. S3 без TLS (`http://`, например свой MinIO
в доверенной сети) — только с `allow_http: true`: без шифрования любой на пути видит данные и
может подменить образ ФС. Если файл читают другие пользователи, демон предупреждает в журнале.

## 4. Быстрый старт

```bash
C=/etc/btrs3fs/creds.yaml
sudo btrs3fs create --creds $C --prefix disks/data --size 10GiB   # один раз: диск + mkfs
sudo mkdir -p /mnt/data
sudo btrs3fs mount --creds $C --prefix disks/data /mnt/data        # корень ФС — root: chown
sudo btrs3fs umount /mnt/data                                      # всё уходит в S3
btrs3fs destroy --creds $C --prefix disks/data --yes               # удалить диск с данными
```

## 5. Команды

| Команда | Назначение |
|---|---|
| `create --creds F --prefix P --size S [параметры §6]` | Записать `P/disk.yaml` и отформатировать в btrfs (все профили `single`). Отказ, если под префиксом есть объекты; при ошибке созданное удаляется. |
| `mount --creds F --prefix P <точка> [-o опции] [--dev-id N] [-r]` | Запустить устройство в фоне и смонтировать с `nosuid,nodev,noatime,lazytime,commit=300` (+ `-o`). Возвращается после монтирования. `-r` — только чтение (ниже). |
| `umount <точка>` | Размонтировать и остановить устройство. |
| `run --creds F --prefix P [--dev-id 0]` | Устройство без монтирования, на переднем плане (systemd, §9). |
| `run --memory --size S` | Устройство в RAM без S3 — для экспериментов. |
| `detach [--dev-id 0]` | Остановить несмонтированное устройство или убрать устройство с умершим демоном. |
| `detach --force [--dev-id N]` | SIGKILL демону даже при смонтированной ФС — как выдернуть питание; дальше `umount <точка>`. |
| `destroy --creds F --prefix P --yes` | Удалить все объекты диска (только его: диск под префиксом `P/…` не трогается). Нужен `P/disk.yaml`. Сначала размонтируйте: команда этого не проверяет. |
| `s3bench --creds F --prefix P [--appends 256,1024]` | Замер для разработки: как читаются объекты, выросшие из мелких дозаписей (PATCH, сегменты, склейка), прямо на уровне S3. Объекты под `P/s3bench-…/` удаляются в конце. |
| `measure --creds F --prefix P` | Измерить связь с S3 с этой машины и напечатать YAML для `--link-config` (§5.1). Читает объекты диска `P` (если он есть), пишет временные под `P/measure-…/` и удаляет их. Полминуты-минута, root не нужен. |

`--prefix`: `/` по краям ничего не значит — `qwe`, `qwe/`, `/qwe` и `/qwe/` это один диск.
`--dev-id`: устройство — `/dev/ublkb<N>`; у `mount` номер по умолчанию выбирает ядро, у `run` и
`detach` — 0.

Флаги `mount` и `run` (задаются при каждом запуске, в `disk.yaml` не хранятся):

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--queues N` | из `disk.yaml` | Число очередей (потоков) устройства. |
| `--link-config FILE` | всё авто | YAML с ручными настройками связи с S3 (§5.1). |
| `--stats-port P` / `--no-stats` | `9470 + N` | Страница статистики (§14). |
| `-r`, `--read-only` | выкл. | Только чтение (ниже). |

**Только чтение** (`--read-only`). Устройство read-only, в бакет демон ничего не пишет — хватает
реквизитов только на чтение (`GET` и листинг). `mount -r` монтирует ФС с `ro,rescue=nologreplay`;
после `run -r` монтировать так же: `mount -o ro,rescue=nologreplay /dev/ublkbN <точка>` — без
`rescue=nologreplay` диск с журналом fsync не смонтируется. Видно состояние на последнюю
фиксацию транзакции. Пока диск смонтирован на чтение, пишущий демон на этом же диске не
запускать. Почему так — SPEC.md §9.2.

Общие флаги: `--log-level L` (`error` … `trace`, синтаксис env_logger, по умолчанию `info`),
`--log-to-stderr`, `--proxy URL` (HTTP(S)-прокси для S3).

### 5.1. Подстройка под связь с S3

Лучшие настройки чтения и выгрузки зависят от того, насколько далеко S3: в облаке рядом с
бакетом и через интернет они различаются в разы и меняются вместе с каналом (VPN). Демон
подстраивается сам: по своим запросам к S3 он оценивает задержку и скорости, а число
одновременных выгрузок и GET наращивает с одного, пока это прибавляет скорость, и уменьшает,
когда скорость падает. Ничего задавать не нужно.

Любую из девяти величин можно задать вручную — файлом `--link-config` (держится до остановки
демона, читается при каждом запуске) или на странице статистики, раздел «S3 link» (до перезапуска).
Пример с комментариями — `examples/link.yaml`:

```yaml
latency: 38 ms              # задержка ответа
read_stream: 277 Mbit/s     # скорость одного GET
read_total: null            # null или нет ключа — авто
write_stream: 201 Mbit/s
uploads: 8                  # одновременных выгрузок
read_cache: 64 MiB          # RAM под окна чтения с запасом; 0 — без них
```

Ключи: характеристики связи `latency`, `read_stream`, `read_total`, `write_stream`,
`write_total`; производные `read_unit` (окно чтения и размер части GET), `fs_readahead` (окно
упреждения btrfs), `uploads`, `reads` (одновременных GET); `read_cache`. Неизвестный ключ —
ошибка запуска.

**Единицы обязательны** (SPEC.md §9.5) — и в файле, и в полях страницы, и в параметрах команд:
время — `38 ms`, `2 s`; скорость — с `/s`, в битах (`300 Mbit/s`, `1.2 Gbit/s`) или байтах
(`40 MB/s`, `37 MiB/s`); размер — `512 KiB`, `16 MiB`, `10 GiB` (двоичные) или `5 MB`, `100 GB`
(десятичные). Пробел между числом и единицей не обязателен. Голое число — только количество
(`uploads: 8`) и ноль (`read_cache: 0`). Буква без единицы (`24M`, `10G`) — ошибка. Выводит
программа так же: трафик с S3 — в битах в секунду, поток данных ядра и кеша — в байтах в секунду,
размеры — в `KiB`/`MiB`/`GiB`.

Готовый файл печатает `btrs3fs measure` и показывает страница статистики
(кнопка «Copy»). Для systemd — `--link-config` в `EXTRA_ARGS` (§9).

Что демон применил и почему, видно в журнале и на странице:

```
S3 link (estimate): latency 38 ms, read 58.7 Mbit/s per stream / 277 Mbit/s total, write 277 Mbit/s per stream / ? total;
applied: read window and GET part 1 MiB, btrfs readahead 16 MiB, 4 parallel uploads, 9 parallel GETs
```

- **окно чтения с запасом** — мелкое чтение выгруженных данных забирает из S3 окно вокруг себя,
  соседние мелкие чтения берутся из RAM (холодное чтение множества мелких файлов — в разы
  быстрее);
- **часть GET** и **окно упреждения btrfs** (`/sys/fs/btrfs/<FSID>/bdi/read_ahead_kb`) — вместе
  задают, сколько GET идут одновременно при чтении больших файлов: демон делит каждый крупный
  запрос на части и забирает их одновременно. Окно упреждения демон ставит, как только видит
  свою ФС смонтированной (и через `mount`, и через fstab), и меняет, когда меняется его
  значение; поменянное вручную держится до следующей смены;
- **число одновременных выгрузок** — общее на все причины.

**Перезамер.** Кнопка «Measure now» на странице: демон дожидается запросов к S3 в полёте, новые
придерживает, меряет не дольше 20 с и отпускает их. Читает существующие объекты диска,
пишет временные (удаляет после; оставшиеся от оборванного замера удаляются при следующем
запуске). На read-only диске меряется только чтение. Итог становится стартом для авто.

Кроме того, демон выключает регулятор фоновой записи ядра (`queue/wbt_lat_usec = 0`): он
тормозит запись, когда чтения медленнее 2 мс, а у S3 они медленные всегда.

## 6. Параметры диска

Задаются при `create`, хранятся в `<prefix>/disk.yaml` и потом не меняются (кроме очередей —
`--queues`).

| Флаг `create` | Поле `disk.yaml` | По умолчанию | Смысл |
|---|---|---|---|
| `--size` | `disk_size` | — | Размер диска, кратен зоне. |
| `--zone-size` | `zone_size` | `16MiB` | Размер зоны = наибольший объект. Степень двойки до 32 MiB; btrfs требует ≥ 4 MiB. Больше 16 MiB не ставьте: Яндекс резко замедляет дозапись в объекты больше ~20 МБ. |
| `--dirty-limit` | `dirty_limit_bytes` | `256MiB` | Несброшенные данные в RAM: сверх — выгрузка в фоне, при двукратном превышении запись ждёт. Не меньше размера зоны: иначе запись размером в зону зависала бы. |
| `--retry-timeout-seconds` | `retry_timeout_seconds` | 60 | Сколько повторять запрос к S3 до ошибки. |
| `--retry-initial-delay-ms` | `retry_initial_delay_ms` | 100 | Первая пауза между повторами, не меньше 1. |
| `--retry-backoff-factor` | `retry_backoff_factor` | 2.0 | Рост паузы, не меньше 1; пауза не длиннее `--retry-timeout-seconds`. |
| `--queues` | `nr_queues` | 4 | Очереди (потоки) устройства. |
| — | `append` | определяет `create` | Как растут объекты зон: `PATCH` (Yandex), `PUT_APPEND` (Ceph RGW Append Object) или `SEGMENTS` (каждая выгрузка — новый объект `<зона>-<смещение>`, фоновая склейка на сервере). |
| — | `copy_min_part` | определяет `create` | `SEGMENTS`: куски меньше этого склейка читает и заливает заново, а не копирует на сервере. `0` — сервер склеивает части любого размера (Selectel, UpCloud); `5M` — только от 5 МиБ (VK Cloud, MinIO, AWS). |
| `--queue-depth` | `queue_depth` | 128 | Глубина очереди. |

## 7. Сохранность данных

Диск ведёт себя как SSD с кешем записи:

- Записанное копится в RAM и уходит в S3 по запросу сброса (`fsync`, `sync`, фиксация
  транзакции btrfs), как только зона заполнена или закрыта, или при превышении
  `--dirty-limit`. Гарантия сохранности — только после сброса.
- `commit=300`: btrfs фиксирует транзакцию раз в 5 минут — без `fsync` при аварии теряется до
  5 минут работы.
- `umount` сбрасывает всё.
- Остановка демона без `umount`, его падение, `detach --force` — как пропадание питания:
  несброшенное теряется (в журнале — «not storing N bytes»). Устройство остаётся и отвечает
  ошибками, ФС аварийно отключается; `btrs3fs umount <точка>` убирает его, повторный `mount`
  поднимает ФС в состоянии последнего сброса.
- S3 недоступен: запрос повторяется `retry_timeout_seconds`, затем `fsync` получает ошибку
  ввода-вывода; данные остаются в RAM, уйдут при следующем сбросе. Невыгруженное читается
  из RAM.

## 8. Логи

- journald: `journalctl -t btrs3fs` (`-f` — в реальном времени); без journald — syslog. В
  файлы не пишутся.
- `--log-to-stderr` — ещё и в терминал. Фоновый демон `mount` пишет в stderr запустившей
  команды, пока работает: не направляйте его в конвейер (`| grep` будет ждать вечно).
- Ошибка, из-за которой команда не выполнилась, всегда печатается в stderr.
- Трассировка запросов ядра к устройству — `--log-level info,requests=trace --log-to-stderr`,
  только в stderr: `sudo btrs3fs --log-level info,requests=trace --log-to-stderr mount … 2>
  /tmp/requests.log`.

## 9. systemd

Шаблон `packaging/btrs3fs@.service` запускает `btrs3fs run` (Type=notify), монтирует fstab.

```bash
sudo install -m 644 packaging/btrs3fs@.service /etc/systemd/system/
sudo install -D -m 600 packaging/example.conf /etc/btrs3fs/main.conf   # отредактировать
sudo systemctl enable --now btrs3fs@main
```

`/etc/btrs3fs/<имя>.conf`: `CREDS`, `PREFIX`, `DEV_ID`, `EXTRA_ARGS` (флаги `run`, §5).
Строка fstab (`x-systemd.requires` размонтирует ФС раньше остановки устройства):

```
/dev/ublkb0 /mnt/data btrfs nosuid,nodev,noatime,lazytime,commit=300,_netdev,x-systemd.requires=btrs3fs@main.service 0 0
```

## 10. Что лежит в бакете

```
<prefix>/disk.yaml            параметры диска (§6)
<prefix>/0000000000000000     зона 0
<prefix>/0000000001000000     зона 1 (смещение 16 МиБ, hex)
<prefix>/0000000002000000-00000000   режим SEGMENTS: зона 2 с начала
<prefix>/0000000002000000-00340000   режим SEGMENTS: следующий фрагмент (смещение в зоне)
```

- Объект зоны появляется при первом сбросе в неё; его размер — сколько данных в зоне. В режиме
  `SEGMENTS` каждый сброс — новый фрагмент `<зона>-<смещение>`, фоновая склейка собирает их в
  `<зона>-00000000`.
- Зона с данными, закрытая btrfs досрочно (FINISH), получает рядом пустой объект-метку
  `<зона>.finished` и после перезапуска остаётся заполненной. Метки вручную не создавайте и не
  удаляйте.
- Метки и фрагменты зоны без её начала — остатки прерванного сброса зоны: демон удаляет их при
  старте. Если сброс зоны не удался из-за S3, чтение и запись этой зоны отдают ошибку, пока btrfs
  не сбросит её снова (в журнале — `RESET failed`).
- Объекты вручную не меняйте. Один диск — один хост (защиты нет).

## 11. Типичные ситуации

| Ситуация | Что делать |
|---|---|
| `disk … not found, create it first` | Неверный `--prefix` или диск не создан. |
| `prefix … already holds N objects` при `create` | Там уже диск: другой префикс или `destroy`. |
| `… disk.yaml exists: a disk cannot lie inside another disk's prefix` при `create` | Префикс внутри другого диска: выберите префикс рядом, а не внутри. |
| `… is already mounted` | Точка занята: `umount` или другая точка. |
| `umount`: ФС занята | Закрыть файлы, выйти из каталога (`fuser -vm /mnt/data`). |
| ФС «пропала», в журнале ядра ошибки ввода-вывода или `emergency shutdown` | Демон умер. `sudo btrs3fs umount <точка>`, затем `mount`. |
| Демон завис, `umount` не помогает | `sudo btrs3fs detach --force --dev-id N`, затем `umount` и `mount`. |
| `fsync` возвращает ошибку ввода-вывода | S3 недоступен дольше `retry_timeout_seconds`; `journalctl -t btrs3fs`. |
| Какие устройства есть | `ls /dev/ublkb*`; зоны — `blkzone report /dev/ublkbN`. |

## 12. Ограничения

- Один хост на диск: защиты от одновременного подключения нет — в том числе одновременно с
  read-only (§5).
- Размер диска после `create` не меняется: на зонированном устройстве этого не позволяют ни ublk,
  ни btrfs (`SPEC.md` §11).
- В режиме `SEGMENTS` у открытых зон в бакете копятся объекты-фрагменты (до 4 × размер зоны /
  окно чтения, при окне 128 КиБ — до 512), пока фоновая склейка их не объединит; заполненные зоны —
  и данных, и метаданных — склеиваются сразу.
- Первое чтение уже выгруженных данных идёт в S3 (десятки–сотни мс на запрос); случайное
  чтение мелких блоков медленное.

## 13. Освобождение места (reclaim)

В zoned-режиме btrfs не перезаписывает на месте: удалённое остаётся мусором в зонах. Зона
освобождается целиком — когда живых данных в ней не осталось или когда btrfs переносит их в
новую зону (reclaim). Перенос стоит чтения живых данных из S3, их записи и удаления объекта,
поэтому перерабатывать стоит редко и самые пустые зоны.

Настройки в `/sys/fs/btrfs/<FSID>/` (`<FSID>` — `findmnt -no UUID /mnt/data`), действуют до
размонтирования:

| Файл | Ядро по умолчанию | btrs3fs | Смысл |
|---|---|---|---|
| `bg_reclaim_threshold` | 75 | 75 | Переработка запускается, только когда распределено ≥ N % диска. **0 выключает её — в zoned так нельзя.** |
| `allocation/{data,metadata}/bg_reclaim_threshold` | 75 | 75 | Перерабатывается зона, заполненная живыми данными меньше чем на N %. |
| `allocation/{data,metadata}/dynamic_reclaim` | 0 | 0 | Порог предыдущей строки ядро считает само: 0, пока нераспределено ≥ 10 зон, и до 99 % по мере исчерпания — переработка только у почти полного диска. Файл `bg_reclaim_threshold` тогда показывает этот порог. |
| `allocation/{data,metadata,system}/periodic_reclaim` | 0 | **1** | Проверять зоны периодически, а не только при освобождении места. |

Демон включает `periodic_reclaim` сам — при каждом монтировании своей ФС (и `btrs3fs mount`,
и fstab), один раз: если потом поменять его вручную, демон не трогает его до следующего
монтирования. В логе — строки `…/periodic_reclaim: enabled`; на ядре старше 6.12 файлов нет, и
демон пишет об этом информационное сообщение.

**Что в итоге работает.** Зоны без живых данных освобождаются всегда (это не reclaim, а удаление
пустых групп): RESET и удаление объектов — но не сразу: пустые группы удаляет фоновый поток
btrfs раз в интервал фиксации (`commit=300` — раз в 5 минут), RESET зон — со следующей
фиксацией, итого до 10 минут; `sync` этого не ускоряет. Последняя группа каждого типа (данные,
метаданные) не удаляется никогда. Освободить сразу и всё — кнопка «Remove empty block groups»
на странице статистики (`btrfs balance start -dusage=0 -musage=0`). Перенос частично заполненных зон (чтение живых данных
из S3, запись заново) начинается, когда распределено ≥ 75 % диска, и берёт зоны с живыми
данными меньше 75 %. Проверка — периодическая: после освобождения хотя бы зоны в сумме фоновый
поток btrfs просматривает зоны и берёт те, в которые не писали с прошлого просмотра.

Перенос зоны, заполненной на 75 %, стоит 3 МБ чтения и записи на освобождённый мегабайт.
Дешевле — порог групп ниже, после монтирования:

```bash
A=/sys/fs/btrfs/$(findmnt -no UUID /mnt/data)/allocation
echo 30 | sudo tee $A/{data,metadata}/bg_reclaim_threshold
```

Порог групп 25–30 — на освобождённый мегабайт ≤ 0,3–0,4 МБ переноса. Выведено из исходников
btrfs 7.2, под нагрузкой не проверялось. Наблюдать — `allocation/*/reclaim_count`,
`reclaim_bytes`, `sudo btrfs filesystem usage /mnt/data`.

## 14. Статистика

Демон показывает статистику на `http://127.0.0.1:<порт>/` (только локально; порт `9470 + N`,
`--stats-port`, `--no-stats`). С другой машины — `ssh -L 9470:127.0.0.1:9470 user@host`.
Если порт занят, устройство работает, в журнале предупреждение. Слева под именем диска — где он лежит (префикс, бакет, адрес S3) и куда смонтирован, устройство, способ дозаписи
(`PATCH`, `PUT_APPEND`, `SEGMENTS`; для `SEGMENTS` — с какого размера куски склейка копирует на
сервере, `copy_min_part`) и время работы.

| Раздел (левая панель) | Что показывает |
|---|---|
| Overview | Сверху — предупреждения (запись ждёт места в RAM, свежие ошибки выгрузки, чтения и склейки, ошибки ввода-вывода ФС) или «All good». Конвейер записи: ядро → буферы RAM (заполнение до жёсткого лимита, отметка мягкого, время до разгрузки) → S3 (выгрузки в работе из допустимых); конвейер чтения под ним зеркально: ядро ← кеш и RAM ← S3, оба S3 справа друг под другом. Графики за 5 минут. Ниже — зоны: карта, кнопки и операции btrfs (описание ниже) и (для `SEGMENTS`) что делает склейка: сколько идёт, ждёт, скорость. Раздробленная открытая зона в `SEGMENTS` — норма: каждая выгрузка добавляет фрагмент, склейка — по порогу числа фрагментов или по простою (SPEC.md §5); частые `fsync` дают много мелких фрагментов в зонах метаданных и суперблока. |
| Overview: Zones | Карта всех зон, клетка на зону по порядку: цвет — состояние, частично записанные заполняются снизу, у закрытых FINISH раньше конца непригодный остаток бледный, красная рамка — данные в RAM, точка — зона из нескольких объектов S3; подробности (в том числе тип: данные или метаданные) при наведении; по клику под картой — всё о зоне: объекты S3 и их размеры, байты в RAM, ждущие выгрузки, идущие сейчас запросы S3 зоны (обновляются вместе с картой), а со стороны btrfs — группа блоков, файлы с данными в зоне (путь и размер) или деревья метаданных; переключатель «All zones / Data / Metadata» приглушает зоны другого типа. Кнопки: выгрузка буферов, склейка, **Commit the filesystem** (`syncfs()` — зафиксировать транзакцию, после этого всё записанное в S3), **Remove empty block groups** (`btrfs balance start -dusage=0 -musage=0` — пустые группы данных, метаданных и системные; их зоны сбрасываются, объекты удаляются); второй balance не начнётся, пока идёт первый (в том числе автоматический), а Commit неактивна, только пока идёт её же `syncfs` и на диске `--read-only`; balance и `syncfs` друг другу не мешают. Идущие операции и результат последней — под кнопками. То же удаление пустых групп демон делает сам — не чаще раза в минуту, когда btrfs освободила место и пустая группа ещё держит зону в S3; **Pause / Resume automatic removal** приостанавливает и возобновляет его (до перезапуска демона). Под картой — текущая операция btrfs: автоматическое удаление (вкл./пауза, когда было и сколько групп), исключительная операция, прогресс balance, глобальный резерв, порог reclaim. |
| S3 link | Девять величин подстройки под связь с S3 (§5.1) и кеш чтения: авто (видно всегда), галочка «manual» с полем ввода (единицы как в файле: `51.8 ms`, `319 Mbit/s`, `8`; Enter применяет, снятая галочка возвращает авто), применённое значение и под ним — на чём оно держится (вручную, замер, сколько запросов; «not enough data» — оценки ещё нет: скорость чтения появляется только при крупных чтениях, примерно за полторы минуты). Состояние регулятора выгрузок и GET и последняя смена с причиной. Кнопка «Measure now» и ход замера. Готовый YAML для `--link-config` с кнопкой «Copy». |
| Details | Последние ошибки с давностью; гистограммы запросов ядра, выгрузок, GET и склейки; размер, которым чтения режутся на параллельные GET; счётчики выгрузок по причинам, чтений по источникам, запросов ядра, склейки. |

Раздел можно открыть ссылкой: `#link`, `#details`.

Кнопка «Concatenate fragmented zones» в карточке зон (диски `SEGMENTS`) ставит в очередь склейки все раздробленные зоны сразу, не дожидаясь порога; то же — `curl -X POST http://127.0.0.1:9470/compact`. Кнопка «Upload buffered data» в карточке буферов выгружает всё из RAM в S3 сразу (`curl -X POST …/flush`); транзакцию btrfs она не фиксирует — для сохранности файлов нужен `sync`. На диске, поданном с `--read-only`, в заголовке страницы — «read-only», Commit the filesystem неактивна, а остальные кнопки (выгрузка, склейка, balance) отвечают ошибкой во всплывающем сообщении. Результат любой кнопки — во всплывающем сообщении в правом нижнем углу. Скорости — в Мбит/с (десятичных, как у сетевых каналов), объёмы — в КиБ/МиБ/ГиБ. Сырые данные — `/stats.json`; счётчики обнуляются при перезапуске демона.
