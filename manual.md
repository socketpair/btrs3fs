# btrs3fs — руководство пользователя

btrs3fs превращает префикс в S3-бакете в диск, на котором живёт файловая система btrfs.
Под капотом — зонированное блочное устройство Linux (ublk, host-managed zoned): каждая зона
диска хранится отдельным объектом в бакете, btrfs работает с ним в zoned-режиме.

Устройство и принятые решения описаны в `SPEC.md`; этот документ — о том, как пользоваться.

## 1. Требования

- **Linux ≥ 6.10** с модулем `ublk_drv` (`CONFIG_BLK_DEV_UBLK`) и поддержкой зонированных
  устройств (`CONFIG_BLK_DEV_ZONED`). Проверено на 7.2.
- **root** для `create`, `mount`, `umount`, `run`, `detach`: зонированное ublk-устройство
  ядро позволяет создавать только привилегированному процессу.
- **Yandex Object Storage** (используется его расширение `PATCH` для дозаписи в объект);
  в бакете должно быть **выключено версионирование**.
- Утилиты: `btrfs-progs` (`mkfs.btrfs`), `util-linux` (`mount`, `umount`), сертификаты CA.
  Полный список пакетов Fedora — `RUNTIME_PACKAGES` в `setup-permissions.sh`.

## 2. Установка

```bash
cargo build --release
sudo install -m 755 target/release/btrs3fs /usr/local/bin/
sudo modprobe ublk_drv
echo ublk_drv | sudo tee /etc/modules-load.d/btrs3fs-ublk.conf   # загрузка модуля при старте
```

Сборка требует Rust и пакетов из `BUILD_PACKAGES` в `setup-permissions.sh`
(`sudo ./setup-permissions.sh build-deps` на Fedora).

## 3. Файл реквизитов

JSON-файл, путь передаётся флагом `--creds`. Реквизиты нигде не печатаются.

```json
{
  "endpoint": "https://storage.yandexcloud.net",
  "region": "ru-central1",
  "bucket": "my-bucket",
  "access_key": "...",
  "secret_key": "..."
}
```

Храните его с правами `0600`, владелец — root (команды запускаются от root):

```bash
sudo install -D -m 600 creds.json /etc/btrs3fs/creds.json
```

## 4. Быстрый старт

```bash
C=/etc/btrs3fs/creds.json

# 1. Создать диск на 10 ГиБ и отформатировать его в btrfs (один раз)
sudo btrs3fs create --creds $C --prefix disks/data --size 10G

# 2. Смонтировать
sudo mkdir -p /mnt/data
sudo btrs3fs mount --creds $C --prefix disks/data /mnt/data

# 3. Работать с /mnt/data как с обычной ФС
#    (корень новой ФС принадлежит root: sudo chown <пользователь> /mnt/data)

# 4. Размонтировать (все данные уходят в S3, демон останавливается)
sudo btrs3fs umount /mnt/data
```

Смонтировать тот же диск снова — шаг 2. Удалить диск со всеми данными:
`btrs3fs destroy --creds $C --prefix disks/data --yes`.

## 5. Команды

| Команда | Назначение |
|---|---|
| `create --creds F --prefix P --size S [параметры]` | Создать диск: записать `P/disk.json` и отформатировать в btrfs (zoned). Отказывается, если под префиксом уже есть объекты. Если форматирование не удалось — созданное удаляется. Параметры — §6. |
| `mount --creds F --prefix P <точка> [-o опции] [--dev-id N] [--queues N]` | Запустить устройство в фоне и смонтировать btrfs с `noatime,lazytime,commit=300`; опции из `-o` добавляются к ним. Возвращается после успешного монтирования. |
| `umount <точка>` | Размонтировать и остановить устройство. |
| `destroy --creds F --prefix P --yes` | Удалить все объекты диска. Сначала размонтируйте диск: команда этого не проверяет. |
| `run --creds F --prefix P [--dev-id 0] [--queues N]` | Устройство без монтирования, на переднем плане (для systemd, §9). |
| `run --memory --size S` | Устройство в RAM без S3 — для экспериментов. |
| `detach [--dev-id 0]` | Остановить несмонтированное устройство (запущенное через `run`), либо убрать устройство, чей демон умер. |
| `detach --force [--dev-id N]` | Убить демон устройства немедленно (SIGKILL), даже если ФС смонтирована — как выдернуть питание. Для зависшего демона. |
| `stats [<точка> \| --dev-id N] [--watch S] [--json]` | Статистика работающего устройства: выгрузки в S3, параллельность, чтения (§14). |

Общие флаги:

| Флаг | Значение |
|---|---|
| `--log-level L` | Уровень логов: `error`, `warn`, `info` (по умолчанию), `debug`, `trace`; синтаксис env_logger, например `debug,libublk=info`. |
| `--log-to-stderr` | Дублировать логи в stderr (цветные на терминале). |
| `--http auto\|http1\|http2` | Версия HTTP к S3; `auto` — HTTP/2, если сервер предлагает. |
| `--proxy URL` | HTTP(S)-прокси для S3, например `http://proxy:3128`. |

`--dev-id`: устройство появляется как `/dev/ublkb<N>`. У `mount` по умолчанию номер выбирает
ядро, у `run` и `detach` — 0.

## 6. Параметры диска

Задаются при `create` и хранятся в `<prefix>/disk.json`; потом не меняются (кроме числа
очередей, которое можно переопределить при `mount`/`run`).

| Флаг `create` | Поле `disk.json` | По умолчанию | Смысл |
|---|---|---|---|
| `--size` | `disk_size` | — | Размер диска; кратен размеру зоны. |
| `--zone-size` | `zone_size` | `16M` | Размер зоны = максимальный размер одного объекта. Степень двойки, не больше 32M. |
| `--max-open-zones` | `max_open_zones` | 1024 | Лимит открытых зон; не меньше числа зон = без лимита. |
| `--max-active-zones` | `max_active_zones` | 1024 | Лимит активных зон; аналогично. |
| `--dirty-limit` | `dirty_limit_bytes` | `256M` | Сколько несброшенных данных держать в RAM; сверх — выгрузка в фоне, при двукратном превышении запись ждёт. |
| `--retry-timeout-seconds` | `retry_timeout_seconds` | 60 | Сколько повторять один запрос к S3, прежде чем вернуть ошибку. |
| `--retry-initial-delay-ms` | `retry_initial_delay_ms` | 100 | Первая пауза между повторами. |
| `--retry-backoff-factor` | `retry_backoff_factor` | 2.0 | Во сколько раз растёт пауза. |
| `--queues` | `nr_queues` | 4 | Очереди (потоки) устройства. |
| `--queue-depth` | `queue_depth` | 128 | Глубина каждой очереди. |

Размер зоны лучше оставить 16M: Yandex Object Storage сильно замедляет дозапись в объекты,
выросшие из многих дозаписей и перевалившие за ~20 МБ (замеры — `SPEC.md` §13.3).

## 7. Сохранность данных

Диск ведёт себя как SSD с кешем записи:

- Записанное сначала копится в RAM и уходит в S3, когда файловая система просит сброс
  (`fsync`, `sync`, фиксация транзакции btrfs) или когда буфер превышает `--dirty-limit`.
- `commit=300`: btrfs фиксирует транзакцию раз в 5 минут. Что записано без `fsync` и не
  попало в фиксацию, при аварии теряется — до 5 минут работы. Важные данные — `fsync`/`sync`.
- `umount` сбрасывает всё: после него в RAM ничего не остаётся.
- Остановка демона без `umount`, его падение или `detach --force` — как пропадание питания:
  не сброшенное не сохраняется (в журнал пишется объём: «not storing N bytes …»), ФС теряет
  диск и аварийно отключается. Повторный `mount` поднимает её в состоянии последнего сброса;
  всё, что было сброшено, цело (проверено `kill -9` демона на смонтированной ФС).
- S3 недоступен: каждый запрос повторяется до `retry_timeout_seconds`; затем `fsync`
  получает ошибку ввода-вывода, данные остаются в RAM и уходят при следующем сбросе, когда
  связь вернётся. Чтение ещё не выгруженных данных идёт из RAM и работает без S3.

## 8. Логи

- Всегда — в journald: `journalctl -t btrs3fs` (`-f` — в реальном времени). Без journald —
  в syslog (`/dev/log`). В файлы не пишутся.
- `--log-to-stderr` — дополнительно в терминал.
- Ошибка, из-за которой команда не выполнилась, печатается в stderr всегда.

## 9. Запуск через systemd

Шаблон `packaging/btrs3fs@.service` запускает `btrs3fs run` (Type=notify), монтирование —
через fstab.

```bash
sudo install -m 644 packaging/btrs3fs@.service /etc/systemd/system/
sudo install -D -m 600 packaging/example.conf /etc/btrs3fs/main.conf   # отредактировать
sudo systemctl enable --now btrs3fs@main
```

`/etc/btrs3fs/<имя>.conf`: `CREDS` (файл реквизитов), `PREFIX` (префикс диска), `DEV_ID`
(номер устройства), `EXTRA_ARGS` (доп. флаги `run`). Строка fstab:

```
/dev/ublkb0 /mnt/data btrfs noatime,lazytime,commit=300,_netdev,x-systemd.requires=btrs3fs@main.service 0 0
```

`x-systemd.requires` гарантирует, что при остановке ФС размонтируется раньше устройства.

## 10. Что лежит в бакете

```
<prefix>/disk.json            параметры диска (§6)
<prefix>/0000000000000000     зона 0
<prefix>/0000000001000000     зона 1 (смещение 16 МиБ, hex)
...
```

Объект зоны появляется, когда в неё впервые что-то сброшено; размер объекта — сколько
данных в зоне. Объекты нельзя менять вручную. Один диск — один хост: подключать диск
одновременно на двух машинах нельзя (защиты от этого нет).

## 11. Типичные ситуации

| Ситуация | Что делать |
|---|---|
| `disk … not found, create it first` | Неверный `--prefix` или диск не создан. |
| `prefix … already holds N objects` при `create` | Под префиксом уже есть диск: другой префикс или `destroy`. |
| `… is already mounted` | Точка занята: `umount` или другая точка. |
| `umount` пишет, что ФС занята | Закрыть файлы и выйти из каталога (`fuser -vm /mnt/data`). |
| ФС «пропала», в журнале ядра `BTRFS … emergency shutdown` | Демон упал или убит. `sudo btrs3fs detach --dev-id N` убирает мёртвое устройство, затем снова `mount`. |
| Демон завис (например, S3 долго недоступен) и `umount` не помогает | `sudo btrs3fs detach --force --dev-id N`, затем `detach --dev-id N` и `mount`. |
| `fsync`/`sync` возвращает ошибку ввода-вывода | S3 недоступен дольше `retry_timeout_seconds`; смотреть `journalctl -t btrs3fs`. |
| Какие устройства есть | `ls /dev/ublkb*`; зоны — `blkzone report /dev/ublkbN`. |

## 12. Ограничения

- Один хост на диск: защиты от одновременного подключения нет.
- Нет кеша чтения: каждое чтение уже выгруженных данных — запрос к S3.
- Нужен Yandex Object Storage: обычный S3 не умеет дозаписывать в объект.
- Состояние «зона закрыта командой FINISH» не сохраняется: после перезапуска такая зона
  видна как закрытая с данными (для btrfs безопасно).

## 13. Освобождение места (reclaim)

В zoned-режиме btrfs не перезаписывает данные на месте: удалённое и перезаписанное остаётся
мусором внутри зон. Зона освобождается целиком — когда в ней не осталось живых данных
(объект зоны удаляется из бакета) или когда btrfs переносит живые данные в новую зону
(reclaim, переработка) и сбрасывает старую.

**Цена переработки в S3:** чтение живых данных из бакета + их запись в новую зону +
удаление объекта. Чем больше живых данных в зоне, тем дороже её переработка, поэтому
перерабатывать стоит редко и самые пустые зоны (btrfs берёт их по возрастанию заполненности).

Настройки — в sysfs, действуют до размонтирования (после каждого `mount` их нужно ставить
заново). `<FSID>` — `findmnt -no UUID /mnt/data`.

| Файл в `/sys/fs/btrfs/<FSID>/` | По умолчанию (zoned) | Смысл |
|---|---|---|
| `bg_reclaim_threshold` | 75 | Общий порог: переработка вообще запускается, только когда распределено ≥ N % диска. **0 выключает её полностью — в zoned-режиме так нельзя**, место рано или поздно кончится. |
| `allocation/{data,metadata}/bg_reclaim_threshold` | 75 | Статический порог: перерабатывается зона, заполненная живыми данными меньше чем на N %. При `dynamic_reclaim=1` не действует и не меняется. |
| `allocation/{data,metadata}/dynamic_reclaim` | 0 | Порог считается сам: 0, пока нераспределённого места не меньше 10 зон, и растёт до 99 % по мере его исчерпания — «перерабатывать ровно столько, сколько нужно». |
| `allocation/{data,metadata}/periodic_reclaim` | 0 | Периодически проверять все зоны по порогу, а не только в момент освобождения места; зоны, куда недавно писали, пропускаются. |

**Рекомендация** — динамическая и периодическая переработка и для данных, и для метаданных,
общий порог не трогать (75):

```bash
A=/sys/fs/btrfs/$(findmnt -no UUID /mnt/data)/allocation
echo 1 | sudo tee $A/{data,metadata}/{dynamic,periodic}_reclaim
```

Метаданные btrfs переписываются при каждом изменении, мусор в их зонах копится быстрее, чем
в зонах данных, а освобождается тоже только переработкой; объём метаданных мал, переносить
их дёшево.

**Оговорка.** С `dynamic_reclaim` переработка начинается поздно: когда нераспределённого места
меньше 10 зон (160 МБ при зоне 16 МиБ) — независимо от размера диска. Если на большом диске
нужен запас свободного места, альтернатива — статический порог: `dynamic_reclaim=0`,
`periodic_reclaim=1`, `allocation/{data,metadata}/bg_reclaim_threshold` = 25–30 (переносятся
зоны, заполненные меньше чем на четверть–треть: на каждый освобождённый мегабайт — не больше
~0,3–0,4 МБ переноса), общий порог 75–80. Рекомендации выведены из устройства механизма
(исходники btrfs, ядро 7.2), под нагрузкой не проверялись.

Наблюдать: `allocation/{data,metadata}/reclaim_count`, `reclaim_bytes`, `reclaim_errors`;
`sudo btrfs filesystem usage /mnt/data`.

## 14. Статистика

```bash
sudo btrs3fs stats /mnt/data            # итоги с момента запуска демона
sudo btrs3fs stats /mnt/data --watch 5  # что произошло за каждые 5 секунд
sudo btrs3fs stats --json               # то же в JSON (единственное устройство)
```

Пример (`fio`, 4 параллельных писателя, `fsync` каждые 8 записей):

```
test/st/ on /dev/ublkb1 (last 4s)
RAM buffers: 1.4 MiB in 3 zones (limit 256.0 MiB); zones: 4 open, 0 closed, 0 full, 124 empty

Uploads to S3: 25 (0 PUT, 25 PATCH), 10.6 MiB, avg 432.6 KiB
  reason:      FLUSH 25, FUA 0, buffer limit 0, explicit 0
  size:        <=64K: 2  <=256K: 2  <=1M: 21
  latency:     p50 <=500ms, p90 <=500ms, p99 <=500ms
  in parallel: 3 now, 4 max; retries 0, failed 0
  zones per FLUSH: 1: 5  2: 5  3-4: 10

Reads: 0 requests, 0 B: from S3 0 B (0 GETs, p50 -, p90 -, p99 -), RAM 0 B, zeros 0 B
Kernel requests: WRITE 84 (11.5 MiB), ZONE_APPEND 0 (0 B), FLUSH 20, FUA 0, zone reset 0, …
  in parallel: 2 now, 4 max
```

| Строка | Что показывает |
|---|---|
| `RAM buffers` | Сколько данных ждёт выгрузки и в скольких зонах; состояние зон. |
| `Uploads to S3` | Дозаписи в объекты: `PUT` — первая запись в зону, `PATCH` — дозапись; объём и средний размер. |
| `reason` | Почему выгружено: `FLUSH` (fsync, sync, фиксация btrfs), `FUA`, `buffer limit` (превышен `--dirty-limit`), `explicit` (форматирование в `create`). |
| `size` | Распределение размеров дозаписей (`<=1M: 21` — 21 дозапись размером от 256 КБ до 1 МБ). |
| `latency` | Время выгрузки: медиана и 90/99-й процентили (с точностью до границы корзины). |
| `in parallel` | Сколько выгрузок идёт сейчас и максимум; максимум — за всё время работы. |
| `zones per FLUSH` | Сколько зон выгружалось за один FLUSH — степень параллельности сброса (до 16 одновременно). |
| `Reads` | Чтения: сколько данных пришло из S3 (и время GET), из RAM, сколько — нули за указателем записи. |
| `Kernel requests` | Запросы ядра к устройству; `ZONE_APPEND` — так btrfs пишет данные, `WRITE` — метаданные и суперблок; `in parallel` — запросы в обработке. |

Статистика есть только у устройств, запущенных `mount` или `run`; отдаёт её сам демон через
сокет `/run/btrs3fs/<N>.sock` (доступ — root). Счётчики обнуляются при перезапуске демона.
